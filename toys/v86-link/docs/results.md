# 計測結果

ヘッドレス Chromium 141（Playwright）、サーバーは `npx http-server`（同じマシンの上）で、`test/e2e.cjs` を2回実行した。
2回とも全項目成功。数値は2回目の実行のもの（1回目もほぼ同じ）。

**この環境は CPU が遅い**（以前のおもちゃで、同じ処理が依頼者の環境の約3倍かかった）。時間は 1/2〜1/3 くらいにして読むとよい。
また、サーバーが同じマシンにあるのでダウンロードはほぼ0秒。インターネット越しなら、下のダウンロードサイズの分だけ足される。

## 起動

| 項目 | 結果 |
| --- | --- |
| ゲスト | Buildroot Linux 6.8（`images/buildroot-bzimage68.bin`）、NIC は ne2k |
| メモリ設定 | `memory_size` = 64MB（1台あたり。v86 のテストと同じ）。ゲストの `free -m` で total 39MB |
| ダウンロードサイズ（初回） | 約12.9MB: イメージ 10.07MB（2台で1回だけ取る）+ v86.wasm 2.01MB + libv86.js 0.36MB + BIOS 0.17MB + xterm.js 0.30MB |
| ブート時間（初回） | 左 11.2s・右 11.6s（「起動」を押してからシェルのプロンプトが出るまで。2台同時） |
| ブート時間（再読込後） | 左 10.9s・右 11.1s |
| 参考: 1台だけ起動 | 5.5s |

**2台は同時に起動する。** 1台だけなら 5.5s、2台同時なら2台とも約11s。v86 はページのメインスレッド（1つの CPU）で動くので、
順番に起動しても1台目が 5.5s、2台目が約11s になるだけで、全体の時間は変わらない。疎通確認には2台とも要るので、
そろって起動する方を選んだ（同時に起動して困ることは起きなかった）。

## メモリ（ページ全体の目安）

| 時点 | レンダラーのメモリ（RSS） |
| --- | --- |
| 起動前 | 118MB |
| 2台が起動した直後 | 467MB |
| ping・HTTP・TCP のあと | 483MB（うち JS ヒープ 215MB） |

2台を動かすと、ページ全体で **約0.5GB**。ゲストのメモリ（64MB × 2）に加えて、v86 の JIT や VGA メモリなどの分がある。

## スナップショット起動（2026-11-20）

`test/measure.cjs` を、スナップショットあり（既定）と `?snapshot=off`（`SNAPSHOT=off`）で、台数ごとに新しいページで測った。
**この環境は上の表の環境より CPU がずっと速い**（通常の起動が 1 台 約 3 秒。上の表は約 10 秒）。比で読むとよい。
サーバーは立てず、`test/serve-route.cjs`（Playwright の route）でファイルを返した。調査は [snapshot-step0.md](snapshot-step0.md)。

## 保存した起動イメージ（段2。2026-11-24）

`test/measure.cjs` を、既定（保存した起動イメージ）・`?snapshot=memory`（段1）・`?snapshot=off` で、台数ごとに新しいコンテキスト（IndexedDB が空）で測った。
既定は、1 回目に開いて全台が準備完了し、テンプレートが IndexedDB に入るのを待ってから読み直し、「2 回目に開いたとき」も測った。
環境は上の「スナップショット起動」と同じ（速い CPU）。サーバーは立てず、`https://v86-link.test/`（`test/serve-route.cjs`）で開いた。

| 台数 | 2 回目（保存から復元） | 1 回目（既定） | `?snapshot=memory` | `?snapshot=off` |
| --- | --- | --- | --- | --- |
| 2 | **1.7 秒**（526MB） | 6.1 秒（479MB） | 5.3 秒（533MB） | 6.8 秒（461MB） |
| 4 | **3.3 秒**（799MB） | 5.8 秒（802MB） | 6.9 秒（726MB） | 13.7 秒（735MB） |
| 8 | **6.1 秒**（1275MB） | 8.8 秒（1140MB） | 11.3 秒（1208MB） | 25.9 秒（1064MB） |

（全台の準備完了。かっこの中はレンダラーの RSS。1 回ずつの計測で、この環境では同じ条件でも 1〜2 秒ばらつく）

- 2 回目は、作る役（1 台目の通常の起動）が無くなり、全台が保存したものから復元する。2 台なら 1〜2 秒台になった
- **4 台・8 台では、まだ 3〜6 秒かかる。** 8 台の 2 回目の内訳（`test/` の外の計測）: 全台がプロンプトに着くまで 0.7〜2.3 秒、
  そのあとのネットワーク設定（netCommand）が 1 台 4〜4.6 秒。復元した VM でも、netCommand は 8 台が同時にゲストの中でコマンドを実行するので遅い
  （1 台だけなら 約 0.5 秒。ゲストでプロセスを 1 つ起動するのに 約 40ms かかり、netCommand は 10 個ほど起動する）。
  `ip` だけの短いコマンドにすると 1 台 約 0.2 秒になる見込み（Node の v86 で測った）。次の改善の候補
- 1 回目（既定）は、段1（`?snapshot=memory`）とほぼ同じ。保存は全台の準備完了のあとに裏で行う（約 1.1 秒）ので、準備完了の時間には入らない
- RSS は、テンプレート（展開した 約 34MB）をページに持つ分と、IndexedDB の読み書きの一時的なバッファで、`?snapshot=off` より 60〜210MB 多い

### 復元を 1 台ずつ順に行う（タイマーの遅れ）

8 台を保存したものから復元して（作る役の通常の起動が入らない条件で）、起動中の 50ms ごとのタイマーの遅れの最大を測った（各 2 回）。

| 復元の仕方 | タイマーの遅れの最大 |
| --- | --- |
| 同時に（段1 まで） | 421 ms・508 ms |
| 1 台ずつ順に、間に一度メインスレッドを空ける（段2） | 80 ms・124 ms |

1 回目（作る役がいる）の遅れの最大（上の表の外。`measure.cjs` の出力）は 168〜476ms で、これは作る役の通常の起動（BIOS → カーネル）の分。
`?snapshot=off`（全台が通常の起動）でも 57〜256ms 出る。
