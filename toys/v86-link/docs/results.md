# 計測結果

ヘッドレス Chromium 141（Playwright）、サーバーは `npx http-server`（同じマシンの上）で、`test/e2e.cjs` を2回実行した。
2回とも全項目成功。数値は2回目の実行のもの（1回目もほぼ同じ）。

**この環境は CPU が遅い**（以前のおもちゃで、同じ処理が依頼者の環境の約3倍かかった）。時間は 1/2〜1/3 くらいにして読むとよい。
また、サーバーが同じマシンにあるのでダウンロードはほぼ0秒。インターネット越しなら、下のダウンロードサイズの分だけ足される。

## 起動

| 項目 | 結果 |
| --- | --- |
| ゲスト | Buildroot Linux 6.8（`images/buildroot-bzimage68.bin`）、NIC は ne2k |
| メモリ設定 | `memory_size` = 64MB（1台あたり。v86 のテストと同じ）。ゲストの `free -m` で total 39MB |
| ダウンロードサイズ（初回） | 約12.9MB: イメージ 10.07MB（2台で1回だけ取る）+ v86.wasm 2.01MB + libv86.js 0.36MB + BIOS 0.17MB + xterm.js 0.30MB |
| ブート時間（初回） | 左 11.2s・右 11.6s（「起動」を押してからシェルのプロンプトが出るまで。2台同時） |
| ブート時間（再読込後） | 左 10.9s・右 11.1s |
| 参考: 1台だけ起動 | 5.5s |

**2台は同時に起動する。** 1台だけなら 5.5s、2台同時なら2台とも約11s。v86 はページのメインスレッド（1つの CPU）で動くので、
順番に起動しても1台目が 5.5s、2台目が約11s になるだけで、全体の時間は変わらない。疎通確認には2台とも要るので、
そろって起動する方を選んだ（同時に起動して困ることは起きなかった）。

## メモリ（ページ全体の目安）

| 時点 | レンダラーのメモリ（RSS） |
| --- | --- |
| 起動前 | 118MB |
| 2台が起動した直後 | 467MB |
| ping・HTTP・TCP のあと | 483MB（うち JS ヒープ 215MB） |

2台を動かすと、ページ全体で **約0.5GB**。ゲストのメモリ（64MB × 2）に加えて、v86 の JIT や VGA メモリなどの分がある。

## 体感の重さ（2台が動いているとき）

| 項目 | 結果 |
| --- | --- |
| ターミナルに1文字送ってから、エコーが表示されるまで | 中央値 15ms、最大 28ms（20回） |
| メインスレッドの遅れ（50ms ごとのタイマーの遅れ）: ブート中 | 中央値 0ms、95パーセンタイル 35ms、最大 223ms |
| 同: 起動後、何もしていないとき | 最大 6ms |

ブート中はときどき 0.1〜0.2 秒ほど引っかかるが、起動後の入力はほぼ遅れを感じない。

## 通信

| 項目 | 結果 |
| --- | --- |
| ping の往復（左→右・右→左、4回ずつ） | 1.3〜9.3ms、平均 約5ms。ARP の解決が要る最初の1回だけ 0.5 秒ほどかかることがある |
| HTTP 取得（左の curl が右の socat + シェルの HTTP サーバーから取得） | 0.40〜0.58s（curl の `time_total`） |
| ケーブルを抜いたとき | `ping -c 3 -W 1` が `100% packet loss`。差し直すと次の ping から通る |
| 遅延 200ms（片道）を足したとき | 往復 402ms |
| COOP/COEP ヘッダ | **不要**。`crossOriginIsolated` が false のまま動く（v86 は SharedArrayBuffer を使わない） |
| 外への通信 | なし（すべて同じサーバーから） |

## N台対応（ハブ / スイッチ）での計測

`test/measure.cjs`（台数ごとに新しいページを開き、全台を同時に起動）と `test/e2e.cjs`（55 項目すべて成功）。環境は上と同じ（遅い CPU）。

### 台数ごとの負荷

| 台数 | 全台の準備完了（起動 + ネットワーク設定） | 1台ごと（ms） | レンダラー RSS | 入力のエコー 中央値 / 最大 | タイマーの遅れ 起動中 p95 / 最大 | 同 起動後 p95 / 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | 13.5 秒 | 11637, 13508 | 412 MB | 11 / 27 ms | 76 / 328 ms | 0 / 7 ms |
| 3 | 22.8 秒 | 22476, 22737, 22738 | 627 MB | 34 / 177 ms | 54 / 218 ms | 211 / 289 ms |
| 4 | 36.0 秒 | 35741, 31935, 32166, 35568 | 824 MB | 64 / 542 ms | 69 / 561 ms | 68 / 277 ms |
| 6 | 59.8 秒 | 57599, 55452, 57193, 57001, 55738, 59497 | 1178 MB | 15 / 315 ms | 119 / 801 ms | 125 / 237 ms |
| 8 | 83.7 秒 | 81750, 83282, 82947, 83019, 82581, 83310, 81325, 83297 | 1576 MB | 18 / 386 ms | 172 / 804 ms | 117 / 625 ms |

- 起動時間は台数にほぼ比例する（1台あたり約 10 秒）。v86 は全台がページのメインスレッドで動くので、同時に起動しても速くはならない
- メモリは1台あたり約 200MB 増える（ゲストの 64MB に、v86 の JIT・VGA メモリなどが加わる）
- 「起動後」は、全台が準備完了してから 3 秒 + 入力の計測のあとの 5 秒間。ゲストの起動後の処理が続いていて、3台以上では 0.1〜0.6 秒ほどの遅れが出た
- 1回ずつの計測なので、ばらつきがある（例: 3台のエコーの中央値 34ms が、6台の 15ms より大きい）

### e2e（3〜4台）

| 項目 | 結果 |
| --- | --- |
| VM を足してから準備完了まで（2台が動いている中で C を追加） | 7.1〜7.9 秒 |
| ハブ: C の tcpdump | A↔B の ICMP 6 件（`6 packets captured`） |
| スイッチ: C の tcpdump | `0 packets captured` |
| MAC フラッディング（偽 MAC 1100 個） | テーブル 1024 件で止まり、覚えられなかった 84 回。C の tcpdump に A↔B の ICMP 6 件 |
| pcap（3台、1138 件） | キャプチャの件数と一致。tcpdump -r で数えた A↔B の ICMP 18 件 = キャプチャの 18 件 |
| 4台 → B を削除 | レンダラー RSS 715MB → 544MB（GC 後、171MB 減） |
| 2台の起動（ネットワーク設定まで） | 約 13 秒（自動のネットワーク設定に約 2.5 秒） |
