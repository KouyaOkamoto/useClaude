# シナリオの受け入れテスト: 検査の方式の調査（ステップ0）

「学習者の操作を邪魔せずに、受け入れテスト（到達性・TCP・HTTP など）を実行する」方法を、4つの案で比べた。
すべて実際に動かして確かめた（2026-11-01。Node 上の v86、既定のイメージ v86net、このリポジトリの `switch.js`）。

- 試作と実験の台本: `test/scenario-step0/probe.mjs`（JS のプローブ）、`test/scenario-step0/exp.mjs`（4案をまとめて試す）
- 実行: `node toys/v86-link/test/scenario-step0/exp.mjs`（v86 を4台動かす。2〜3分）
- 構成: サーバー A（10.5.0.2、BusyBox httpd が 80 番）・クライアント B（10.5.0.3、`uart1` あり）・ルーター R（10.5.0.1 と 203.0.113.1、転送 ON）・
  検査用 VM C（10.5.0.4）を1台のスイッチに。プローブは 10.5.0.99（同じセグメント）と 203.0.113.10（ルーターの外。「インターネット側」の役）

## 結果

### a. JS のプローブ（スイッチのポートに、JS で作ったノードをつなぐ）

VmNode と同じ形（`on('frame')` / `injectFrame()`）のオブジェクトなので、`VirtualSwitch.addPort()` にそのままつながる。
ARP（引く・答える）、ICMP echo、TCP の SYN、TCP の上の HTTP/1.0 の GET を実装した。

| 検査 | 結果 |
| --- | --- |
| ping A（同じセグメント） | 成功、TTL 64 |
| ping 存在しないアドレス | 失敗（ARP が引けない）を判定できた |
| TCP 80（httpd） | open（SYN → SYN-ACK。すぐ RST で閉じる） |
| TCP 23（待ち受けなし） | closed（SYN → RST） |
| HTTP GET `/` / `/nothing` | 200・本文 `hello-from-A` / 404 |
| ルーターの外（203.0.113.10）から ping A・HTTP GET | 成功、TTL 63（ルーターで 1 減る）・200 |
| ルーターの外から TTL 1 で ping | ルーターが返す Time exceeded（送り元 203.0.113.1）を判定できた |
| 9 つの検査にかかった時間 | 2.3 秒 |
| A の端末への表示 | なし（ゲストを操作しないので） |
| 検査のあと A に残った TCP の接続（LISTEN 以外） | 0（open の判定は RST、HTTP は FIN で閉じる） |
| 壊れたフレーム（短い・壊れた IP ヘッダ・途中で切れた ARP）を入れる | 例外なし（無視する） |

- 実装量: 試作で 211 行（空行・コメントを除き 191 行）。本番では、TCP の再送・順番の乱れの扱い・タイムアウトの整理・単体テストで、300〜400 行の見込み
- 制約: 学習者の VM の中の設定（デフォルトゲートウェイ・ルーティングテーブル）からの到達は確かめられない（プローブは自分の設定で送るため）。
  プローブの通信はスイッチを通るので、キャプチャに現れる（「検査」と分かるように印を付けて表示できる）

### b. 隠しの検査用 VM（シナリオが用意する、学習者から見えない VM）

C から `wget`・`nc -z`・`ping` を実行して、A の 80 番が開いている・23 番が閉じている・ping が通ることを確かめられた（0.2〜0.25 秒）。

- コスト: VM を1台足すと、ブラウザのメモリが約 200MB 増え（2 台 739MB → 4 台 1,143MB。`docs/buildroot-image.md`）、起動の時間も延びる。
  スイッチのポートを1つ使う
- 制約: 検査用 VM は学習者の PC そのものではないので、学習者の PC の設定（ゲートウェイの設定し忘れなど）は確かめられない

### c. 学習者の VM の端末（ttyS0）に、マーカーつきでコマンドを入れる

- 学習者が途中まで打っていた `ifcon` と、検査のコマンドがつながり、`ifconwget: not found` になった（実際に衝突した）
- 学習者が前景で `ping -c 4` を動かしている間に入れると、ping が終わるまで待たされた。検査のコマンドと出力は、学習者の端末に表示される

→ 学習者の端末を邪魔しない、という条件を満たせない

### d. 2本目のシリアル（ttyS1）を検査専用にする

- 同梱の v86（0.5.472）は `uart1: true` で2本目の UART（0x2F8・IRQ 3）を持てる。出力は `serial1-output-byte`、入力は `serial_send_bytes(1, …)`
- v86net のカーネルは ttyS0〜3 を持つ（`CONFIG_SERIAL_8250_NR_UARTS=4`）。ttyS1 の UART も 16550A として認識された
- B の ttyS0 で学習者が前景の `ping -c 6` を動かしている間に、ttyS1 のシェルから `wget`・`nc -z` を実行できた（0.1〜0.3 秒）。
  ttyS0（学習者の端末）には何も出ず、ping も最後まで動いた
- ttyS1 のシェルの起動: 実験では ttyS0 から `setsid sh -c 'exec /bin/sh -i </dev/ttyS1 >/dev/ttyS1 2>&1'` を1回実行した。
  本番は、イメージの `/etc/inittab` に `ttyS1::respawn:…` を足す（イメージの作り直しが要る）か、ネットワーク設定のコマンドと一緒に1回起動する
- 実装量: v86 のオプション1つと、シリアルの読み書き・マーカーの解析（既存の `run` と同じもの）。100 行程度
- 制約・注意:
  - 学習者の VM の中で、root のシェルとして動く。学習者が `ps` で見えるし、`kill` できる（壊れたら検査は「エラー」になる。起動し直せる）
  - 検査の通信は、学習者の VM から本当に出る。iptables のカウンタ・conntrack・ARP の表に跡が残る（ただし、学習者がふつうに通信したときと同じ種類の跡）
  - 以前のイメージ（`?image=buildroot68`）でも ttyS1 はある見込みだが、確かめていない

| | a. JS のプローブ | b. 隠しの検査用 VM | c. 学習者の端末 | d. 2本目のシリアル |
| --- | --- | --- | --- | --- |
| 学習者の端末を邪魔しない | ○（ゲストを操作しない） | ○ | ×（入力とつながる・待たされる・表示される） | ○（ttyS0 に何も出ない） |
| 内側（学習者の PC）からの検査 | ×（プローブ自身の設定で送る） | △（同じセグメントの「別の PC」から） | ○ | ○（学習者の PC そのものから。ゲートウェイの設定も反映される） |
| 外部・中立の観測（「インターネット側のホスト」「外部のユーザー」） | ○（任意のアドレスで置ける） | △（VM を足すと重い） | × | × |
| 実装量 | 中（300〜400 行） | 小（既存の VM の仕組み） | 小 | 小（100 行程度） |
| 重さ | 軽い（JS だけ） | 重い（VM 1台 約 200MB、起動の時間） | 軽い | 軽い |
| 壊れやすさ | 低い（自前の小さなスタック。ゲストに依存しない） | 中（VM の起動・シェルの出力の解析） | 高い | 中（シェルの出力の解析。学習者が ttyS1 のシェルを止められる） |

キャプチャの条件（「検査中に、あるセグメントに特定のプロトコルのフレームが現れない」）は、どの案でもなく、
仮想スイッチの `onFrame`（キャプチャと同じ出どころ）を検査の間だけ見ればよい（ゲストもプローブも要らない）。

## 推奨（実装の前に判断をお願いする）

**a と d の併用**（キャプチャの条件はスイッチの観測で）:

- **外から・中立の検査は a**: 「外部のユーザーから Web が見える」「インターネット側のホストから到達できない」「ある VLAN のセグメントから届かない」など。
  プローブは、シナリオが置き場所（ポート・VLAN・IP・ゲートウェイ）を決める。学習者には見えない（または「検査用」として図に出す）
- **内側からの検査は d**: 「社員 PC からサーバーの 80 番に届く」「社員 PC のデフォルトゲートウェイが正しい」など、学習者の PC の設定が効く検査
- **b は使わない**（重い。学習者の PC の設定を確かめられない）。**c は使わない**（端末を邪魔する）
- 検査の実行層は、アダプタ（`probe`・`vmShell`・`switchObserver`）として差し替えられるようにする

決めていただきたいこと:

1. **a と d の併用でよいか**
2. **d の ttyS1 のシェルをどう起動するか**
   - (i) v86net のイメージの inittab に `ttyS1::respawn:/bin/sh` を足し、イメージを作り直して公開し直す（学習者の端末に何も出ない。いちばんきれい）
   - (ii) いまのイメージのまま、起動後のネットワーク設定のコマンドと一緒に、ttyS0 から1回だけ起動する
     （いまもネットワーク設定のコマンドは端末に1回表示されている。その行が少し長くなる）
   - 推奨は、まず (ii) で作り、あとで (i) に移る（イメージの作り直しを今回の作業の前提にしないため）
3. **プローブの通信をキャプチャにどう出すか**: 推奨は「キャプチャに残し、経路の列に『検査』と印を付ける」
   （失敗した検査の通信を一覧で確かめられる。依頼の任意の項目に使える）
4. **シナリオモードは v86net のイメージに限ってよいか**（以前のイメージは iptables・VLAN が無いので、S2 ができない）
