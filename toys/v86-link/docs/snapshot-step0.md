# スナップショット起動の調査（ステップ0）

VM の起動を速くするために、v86 のスナップショット（`save_state` / `restore_state`）が使えるかを確かめた（2026-11-20）。
本体（`main.js` など）は変えていない。Node 上の v86（同梱の `lib/v86/libv86.js`、0.5.472）と、本体と同じ CSP のページを
ヘッドレス Chromium で動かして確かめた。イメージは既定の v86net、`memory_size` は 64MB。

- 実験の台本: `test/snapshot-step0/exp.mjs`（Node。項目 1〜7 と、壊れた状態）、`test/snapshot-step0/browser.cjs` + `browser.html` / `browser.js`（ブラウザでの時間とメモリ）
- 実行: `node --expose-gc toys/v86-link/test/snapshot-step0/exp.mjs`（1〜2 分）/ `node toys/v86-link/test/snapshot-step0/browser.cjs`（約 1 分。サーバーは要らない。Playwright の route でファイルを返す）
- 共通部分: `test/snapshot-step0/common.mjs`（v86 を VmNode と同じ形で包む）

**この環境は CPU が速い**（通常の起動が 1 台 約 2〜3 秒。`docs/results.md` の環境は約 10 秒）。時間は絶対値より、通常の起動との比で読むとよい。

## 結論

**使える。** 8 台で、全台がプロンプトに着くまでが 17.4 秒 → 1.0 秒になった（ブラウザ）。注意が要るのは次の 3 つ。

1. 復元した直後の数百ミリ秒、**全台のゲストの乱数が同じ**になる。`/dev/urandom` に書いても、すぐには分かれない（約 1 秒で分かれる）
2. 復元に失敗すると、**`initial_state` では例外を受け取れず、VM は起動しないまま**になる。`restore_state()` なら受け取れる
3. 状態が途中まで書き戻されたあとの失敗（uart1 の有無の違い）では、同じ VM で起動を続けると**スレッドが止まる**ことがある。作り直す

## 結果

### 1. save → restore が通るか・イメージを渡し直す必要があるか

| 方式 | プロンプトまで | 結果 |
| --- | --- | --- |
| 方式A: `new V86({ initial_state })`、bzimage・BIOS も渡す | 0.32 秒 | 動く |
| 方式A: `initial_state` だけ（bzimage・BIOS・cmdline を渡さない） | 0.22 秒 | 動く |
| 方式B: bzimage・BIOS を渡さず `autostart: false` で作り、`emulator-ready` のあと `restore_state()` → `run()` | 0.20 秒 | 動く |
| 方式B: bzimage・BIOS を渡して `autostart: false`、`emulator-ready` のあと `restore_state()` → `run()` | 0.21 秒 | 動く |
| 方式B: ふつうに起動を始め、BIOS の途中で `restore_state()`（動いている VM を上書き） | 0.51 秒 | 動く |

- **bzimage・BIOS は渡さなくてよい**。状態にメモリ・デバイス・CPU がすべて入っているので、イメージの展開も BIOS も通らない
- ただし、失敗したときに通常の起動へ切り替えるなら、bzimage・BIOS を渡しておく（下の「壊れた状態」）。イメージはページが 1 回だけダウンロードしたものを使うので、渡す手間はほぼない

### 2. 状態のサイズ・時間

| 項目 | Node | ブラウザ（Chromium） |
| --- | --- | --- |
| 状態のサイズ（プロンプトの時点） | 34.4MB | 34.4MB |
| `CompressionStream('gzip')` で圧縮したあと | 8.6MB（25%） | 8.6MB |
| `save_state` の時間 | 60〜110ms | 59ms |
| gzip の時間 / 展開の時間 | 0.48 秒 / 0.23 秒 | 0.63 秒 / 0.12 秒 |
| 復元（`emulator-started` まで） | 0.08〜0.12 秒 | — |
| 参考: ネットワーク設定のあと、2MB のファイルを作って消したあとの状態 | 34.9MB、圧縮後 10.4MB | — |

- 状態は 64MB のメモリより小さい（v86 が中身が 0 のページを省いている）。uart1 の有無でサイズはほぼ変わらない
- ページの中だけで持つなら、圧縮は要らない（34MB の `ArrayBuffer` を 1 つ持つだけ）。IndexedDB に置くときは圧縮すると 1/4 になる
- gzip を展開した状態からも、そのまま復元できた

**台数ごとの時間とメモリ（ブラウザ。テンプレート用の 1 台を動かしたまま、さらに n 台を同時に復元）**

| 台数 | 復元して全台がプロンプトに着くまで | 通常の起動で全台がプロンプトに着くまで | レンダラーの RSS（復元した n 台が動いている間） |
| --- | --- | --- | --- |
| 2 | 0.31 秒 | 4.8 秒 | 472MB |
| 4 | 0.53 秒 | 8.9 秒 | 722MB |
| 8 | 1.02 秒 | 17.4 秒 | 1,207MB |

- 復元は 1 台あたり約 0.13 秒（メインスレッドで順に処理される）。通常の起動は 1 台あたり約 2.2 秒
- テンプレートを作る 1 台目は通常どおり起動するので、「全台の準備完了」は「1 台目の起動 + n × 0.13 秒 + ネットワーク設定」になる見込み
- 復元した VM 1 台あたり、レンダラーの RSS は約 120MB 増える（8 台で 1,207 − 237 = 970MB）。テンプレートを持つ分（34MB）はページに 1 つだけ

### 3. 復元した VM を同時に動かす

テンプレートを作った VM（通常の起動。10.5.0.2）と、そこから復元した 3 台を 1 台のスイッチにつなぎ、`main.js` の netCommand と同じコマンドで MAC・IP・ホスト名を変えた。

| 項目 | 結果 |
| --- | --- |
| 3 台の netCommand（同時に） | 全台 NET-OK、0.6〜0.9 秒 |
| ping（V1→V2、V2→V3、V3→V1、V1→テンプレートを作った VM） | すべて 2/2 |
| TCP（V1 で `nc -l` を 2 つ、V2・V3 から同時に送る） | 両方届いた |
| TCP の送り元ポート・ISN | 2 台で違う（例: 37659 / 45493） |
| netCommand のあとの MAC アドレステーブル | 4 台の新しい MAC（02:00:0a:05:00:…）だけ。00:22:15:… は入っていない |

### 4. uart1 あり / なしの違い

| 保存した VM | 復元する VM | 結果 |
| --- | --- | --- |
| uart1 あり | uart1 あり | 動く。ttyS1 のシェルも使える |
| uart1 あり | uart1 なし | 動く（ttyS0 は使える） |
| uart1 なし | uart1 あり（`initial_state`） | **起動しない**。`emulator-started` が来ない。例外 `Cannot read properties of null (reading '0')` は呼び出し側では受け取れない（Node の uncaughtException。ブラウザでは window の error になる） |
| uart1 なし | uart1 あり（`restore_state()`） | `restore_state()` が同じ例外で reject する（受け取れる）。ただし状態が途中まで書き戻されていて、そのまま `run()` すると呼び出しのスタックがあふれ、スレッドが止まって戻らないことがあった |

→ テンプレートは uart1 の有無ごとに分けて持つ（シナリオモードは uart1 あり、自由構成も v86net では uart1 あり。いまは同じ）。

### 5. 復元直後の状態

| 項目 | 結果 |
| --- | --- |
| ne2k の MAC | **全台同じ**（テンプレートの起動のときのランダムな値。例: 00:22:15:d4:45:20） |
| eth0 の状態 | **DOWN**（v86net はブートで eth0 を上げない。上げるのは netCommand） |
| MAC を変える前にゲストが出すフレーム | **なし**。何も入力せず 3 秒待っても、3 台とも 0 個（eth0 が DOWN なので、IPv6 の DAD も ARP も出ない）。MAC アドレステーブルも空のまま |
| 乱数（`/proc/sys/kernel/random/uuid`・`/dev/urandom`） | 復元してすぐに読むと**全台同じ**。1 秒後には分かれた（書かなくても） |
| `/dev/urandom` に 64 バイト書いたあと | 書いた直後は**まだ全台同じ**（書いた内容は次の再シードまで使われない）。1 秒後には分かれた |
| 時計（`date`） | **テンプレートを保存した時刻から進む**。保存から 12 秒後に復元すると、ゲストは 6 秒遅れていた（復元までの時間の分だけ遅れる）。`date -s @秒` で合わせられた（ずれ 0 秒） |
| 稼働時間（`/proc/uptime`） | テンプレートの値から続く（約 5 秒） |
| プロンプトの検出 | 復元しただけでは新しい出力が無く、プロンプトは出ない。`"\n"` を送ると、0.1 秒以内に `~% ` が出た |

乱数について:

- Linux 6.12 の乱数生成器（crng）は、起動して間もない間は短い間隔（稼働時間の半分、最低 1 秒）で再シードする。
  テンプレートは稼働 2 秒前後で保存するので、復元後 1〜3 秒で再シードされ、そのときに割り込みのタイミング（台ごとに違う）と、書き込んだ値が混ざる
- `/dev/urandom` への書き込みは、すぐの再シードを起こさない（すぐに分けるには `RNDRESEEDCRNG` の ioctl が要るが、BusyBox には呼ぶ手段が無い）
- 書かなくても分かれたのは、割り込みのタイミングがたまたま違ったから。確実に分けるには、書き込み（ホストの `crypto.getRandomValues`）が要る
- いまの流れで乱数を使う最初のもの（TCP の送り元ポート・ISN、`mktemp` など）は、netCommand のあと（復元から 1 秒以上あと）に来る。項目 3 の送り元ポートは違っていた

### 6. シナリオ用: ttyS1 のシェルを起動したあとの状態

uart1 ありの VM で、`scenarioui.js` の setupVm と同じく `hostname` と `vmshell.js` の `BOOTSTRAP` を実行し、`VmShell.alive()` が通ってから保存した。そこから 2 台を復元した。

| 項目 | 結果 |
| --- | --- |
| 復元した VM で `VmShell.alive()` | 2 台とも true（最初の 1 回で） |
| `VmShell.route()`・`shell('hostname; ip link …')` | 動いた（ホスト名はテンプレートの `s`。MAC は 2 台とも同じ 00:22:15:…） |
| ttyS0 のプロンプト | `"\n"` で出た |

→ シナリオでは、ttyS1 のシェルまで起動した状態をテンプレートにできる。復元したあとは、setupVm の「MAC を決まった値に」以降（`ifconfig eth0 hw ether …`、シナリオの init）だけを実行すればよい。

| 確かめ方 | 結果 |
| --- | --- |
| ブラウザ: 2・4・8 台を復元して `destroy()` | レンダラーの RSS が 472 → 252MB、722 → 280MB、1,207 → 321MB に戻った |
| ブラウザ: 4 台の復元 → `destroy()` を 10 回 | 538、514、483、477、482、483、477、496、481、485MB（増え続けない） |

### 参考: 壊れた状態を渡したとき

| 壊し方 | `initial_state` で渡す | `restore_state()`（イメージを渡し `autostart: false`）で渡す |
| --- | --- | --- |
| 先頭 1MB だけ | 起動しない。`Length doesn't match header` は受け取れない | reject する → 同じ VM で `run()` して、通常の起動でプロンプトに着いた（2.3 秒） |
| ヘッダを壊す | 起動しない。`Invalid header` は受け取れない | 同上（2.1 秒） |
| 本文に雑音（先頭の JSON にかかる） | 起動しない。JSON の解析の例外は受け取れない | 同上（2.3 秒） |

- 状態の検査は、ヘッダ（マジック・版 6・長さ）と、デバイスの状態の JSON の解析だけ。**メモリの部分が壊れていても検出しない**（IndexedDB に置く段 2 では、ハッシュを一緒に持って確かめる）
- 状態の版（`STATE_VERSION` = 6）が違うと `Version mismatch` になる。v86 を更新したら、古いテンプレートは使えない

## 推奨する方式

**方式B（`restore_state()`）で、bzimage・BIOS も渡して作る:**

```js
const e = new V86({ ...いまの設定（bzimage・BIOS・uart1）, autostart: false });
await once(e, 'emulator-ready');
try {
  await e.restore_state(template.slice(0));   // 失敗は reject で受け取れる
  e.run();
  // 復元の経路へ（MAC のフレームを止める → "\n" → 乱数・時計 → netCommand）
} catch (err) {
  // ヘッダ・長さ・JSON の失敗なら、同じ VM で e.run() すれば通常の起動になる。
  // ただし、途中まで書き戻された失敗（uart1 の違いなど）は区別できないので、いつも destroy して作り直すのが安全
}
```

- 方式A（`initial_state`）は、失敗を受け取れない（`emulator-started` が来ないのをタイムアウトで待つしかない）ので使わない
- 失敗したときは、**いつも `destroy()` して通常の起動で作り直す**。同じ VM で `run()` するのは、ヘッダの失敗なら動いたが、uart1 の違いではスレッドが止まった。失敗の種類で分けるより、作り直す方が安全
- テンプレートのキーは「イメージ・v86 の版（状態の版）・`memory_size`・uart1」。いまは自由構成もシナリオも v86net なら uart1 ありなので、実質 1 つ
- テンプレートはプロンプトの時点（eth0 が DOWN、ネットワーク未設定）で取る。シナリオは、ttyS1 のシェルまで起動した時点で別に取る

## 次の実装でどうするか

1 台目を通常どおり起動し、プロンプトが出た時点で `save_state` してテンプレートをメモリに持ち、2 台目以降は方式B で復元する。
復元した VM は eth0 が DOWN のまま起きるので、MAC を変える前のフレームは出ない（今回の実験では 0 個）が、同じ MAC の VM が並ぶことに変わりはないので、
念のため「NET-OK までは、その VM のポートのフレームを捨てる（キャプチャには理由を残す）」をスイッチ側に入れる。乱数は、復元してすぐ
ホストの `crypto.getRandomValues` の値を `/dev/urandom` に書き、`date -s @秒` で時計を合わせる。書き込みは次の再シード（復元から約 1 秒）で効く。
netCommand と同じコマンドの先頭に入れれば、学習者が乱数を使う通信（TCP の接続など）を始めるころには分かれているが、e2e で 2 台の uuid が違うことを確かめる。シナリオは、ttyS1 のシェルを起動した状態を別のテンプレートにし、
setupVm の MAC の設定と init だけを復元のあとに実行する。復元に失敗したら、いつも `destroy()` して通常の起動で作り直す。

## 段2 で確かめたこと（2026-11-24）

段1（メモリのテンプレート）を入れたあと、段2（IndexedDB に保存）の前に確かめた。

### NET-OK まで捨てていたフレーム

段1 の e2e で「NET-OK の前に捨てたフレーム 4 件」が出ていた。8 台（1 台を通常の起動、7 台を復元）で、捨てたものを全部調べた。

| 送り元 MAC | 種類 | 件数 |
| --- | --- | --- |
| その VM に **割り当てた** MAC（02:00:0a:05:00:…） | IPv6 の MLD（Hop-by-Hop。マルチキャストのグループへの参加） | 7（全台 1 件ずつ） |
| 同上 | ICMPv6 の Neighbor solicitation（DAD） | 1 |
| ne2k の元の MAC（00:22:15:…） | — | **0** |

どれも、netCommand で MAC を変えて `ifconfig eth0 … up` した直後から、NET-OK を出すまでの間に出た、正当なフレームだった
（復元した VM は eth0 が DOWN で起きるので、元の MAC のフレームは出ない。段1 の調査の項目 5 と同じ）。
→ 捨てる条件を「**送り元 MAC が、その VM に割り当てた MAC と違うフレームだけ**」に絞った（`switch.js` の `setHold(port, true, { allow })`）。
ne2k の元の MAC のフレームは引き続き捨て、MAC テーブルにも入れない。変えたあと、e2e で捨てたフレームは 0 件、MAC テーブルに 00:22:15:… が入った回数も 0 だった。

### restore_state に渡すバッファ

Node の v86 で、テンプレート（34MB）を複製せずに `restore_state` に渡して確かめた。

| 確かめたこと | 結果 |
| --- | --- |
| 復元の前後で、テンプレートの SHA-256 | 変わらない |
| 復元した VM で 4MB のファイルを書いたあとの、テンプレートの SHA-256 | 変わらない（VM のメモリはテンプレートと別） |
| 1 台目が動いている間に、同じバッファから 2 台目を復元 | 動く。2 台目には 1 台目が書いたファイルが無い |
| 復元のあとのバッファの大きさ | 変わらない（detach されない） |

→ `restore_state` は渡したバッファを書き換えず、持ち続けもしない。`vm.js` で複製（`template.slice(0)`）をやめた（1 台あたり 34MB の一時的な複製が無くなる）。

### 復元する VM のカーネル（bzimage）

段1 の調査の項目 1 のとおり、方式B（`autostart: false` → `restore_state` → `run`）は bzimage・BIOS を渡さなくても動く。
段1 では「失敗したら同じ VM で通常の起動に切り替える」ために渡していたが、失敗したらいつも作り直す（`destroy()` → 新しい VM）ことにしたので要らない。
→ 復元する VM には bzimage（6MB の複製）も BIOS も渡さない。

### 保存した起動イメージ（IndexedDB）

| 項目 | 結果（ブラウザ） |
| --- | --- |
| 保存する大きさ | gzip で 8.2MB（展開すると 32.8MB） |
| 保存（SHA-256 と圧縮・書き込み） | 約 1.1 秒。全台の準備完了のあと、裏で行う |
| 読み出し（読み込み・展開・SHA-256） | 約 0.2〜0.25 秒 |
| 安全な接続でないページ（http で、localhost 以外） | `crypto.subtle` が無く SHA-256 を計算できないので、メモリだけで動く |
