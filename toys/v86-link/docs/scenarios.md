# シナリオ（要件から設計・構築して検証する）

依頼文と要件を読み、学習者がネットワークを設計・設定して、「検査する」で受け入れテストを実行する仕組み。
検査の方式を選んだ調査は [scenario-step0.md](scenario-step0.md)。

> **自習向けの自動判定で、不正を防ぐ仕組みではない。** 学習者は自分の VM の中で何でもできる（検査用のシェルを止める・
> 出力を細工するなど）。そのため、検査の多くは **外部からの検査（プローブ）** でも確かめている。
> 外部からの検査（プローブ）は、学習者の VM の細工の影響を受けにくい（VM の外、スイッチのポートにつないだ JS のノードが、
> 実際にパケットを送って返事を見るため）。それでも、ページの JavaScript を書き換えれば何でも「合格」にできる。

## 使い方

- 画面上の「シナリオ」から選ぶか、URL に `?scenario=small-office` のように付けて開く
- 「ファイル…」で、手元のシナリオの JSON を読み込める（信用できない入力として扱う。下の「セキュリティ」）
- 開くと、構成を作り、VM を起動して、初期設定を入れる（数十秒）。終わると端末を学習者に渡す
- 「検査する」で、全部の検査を1つずつ実行し、要件ごとに **合格 / 不合格 / 未実行 / エラー** を表示する
- 「最初からやり直す」で、VM・プローブ・スイッチの設定を全部作り直す（MAC テーブル・キャプチャも空にする）
- 「ヒントを見る」で、ヒントを段階ごとに1つずつ表示する。全部合格すると解説（debrief）が読める
- 「検査の通信を見る」で、キャプチャを検査の通信（`probe`）だけに絞る
- シナリオを選ぶのをやめる（「なし」）と、ページを読み直して自由構成に戻る

**シナリオモードは、新しいイメージ（v86net）だけで動く**（ttyS1・iptables・8021q・httpd などを使うため）。
`?image=…` で以前のイメージを選んでいると、その旨を画面に表示して、構成を作らない。

## 同梱のシナリオ

| ID | 題 | 難易度 | 内容 |
| --- | --- | --- | --- |
| `small-office` | S1 小さなオフィス | 易 | 2つのサブネット＋ルーター。社員 PC にゲートウェイが無く、ルーターの転送が OFF（壊れた初期設定から直す、トラブルシュート型） |
| `dept-vlan` | S2 部署分離 | 中 | 1台のスイッチを VLAN 10/20 に分け、ルーターの iptables（FORWARD）で、営業 → 開発の Web（80番）だけを通す。ブロードキャストの分離はキャプチャの条件で確かめる |

**模範解答は `test/scenario-answers/` にあるため、自習するときは見ない。**（公開のディレクトリ `scenarios/` には置いていない）

## 仕組み

```
scenarios/*.json ──▶ scenario/schema.js（検証。通らなければ読み込まない）
                          │
                          ▼
scenarioui.js（画面・構成の作成・アダプタ）
   │  VM: main.js の createMachine / bootMachine（ttyS0 = 学習者の端末、ttyS1 = 検査用のシェル）
   │  プローブ: probe.js（スイッチの P9〜P12 につなぐ JS のノード。画面には出さない）
   ▼
scenario/evaluate.js（検査を1つずつ実行して判定。DOM・v86 に依存しない）
   ├─ probe アダプタ   … probe.js（ping・TCP 接続・HTTP GET を、JS がパケットを組み立てて行う）
   ├─ vm アダプタ      … vmshell.js（ttyS1 のシェルで ping・nc・wget・ip route を実行して出力を解析）
   └─ capture アダプタ … scenario/observe.js（スイッチの onFrame を検査の間だけ集める）
```

- 読み込み・検証・判定は純粋なモジュール（DOM も v86 も使わない）で、Node の単体テストで確かめている
- 検査の実行層はアダプタで差し替えられる（単体テストでは偽のアダプタ、結合テストでは本物）
- VmNode・スイッチ・キャプチャは壊していない（足したのは、2本目のシリアル `uart1` と、キャプチャの記録の `probe` の印だけ）

### 検査用のシェル（ttyS1）

学習者の端末（ttyS0）と衝突しないよう、検査のコマンドは2本目のシリアル（ttyS1）のシェルで実行する。

1. シナリオの起動中、学習者に端末を渡す前に、ttyS0 で **1回だけ** 次を実行して ttyS1 にシェルを起動する
   ```
   (setsid sh -c 'stty -echo </dev/ttyS1; PS1= PS2= exec /bin/sh </dev/ttyS1 >/dev/ttyS1 2>&1' &)
   ```
2. シナリオの初期設定（`init`）は ttyS1 で実行する（学習者の端末に出さない）
3. 端末の表示をクリアして、学習者に渡す
4. 検査のコマンドは ttyS1 だけに送る。**ttyS0 には検査のコマンドを入れない**

学習者が ttyS1 のシェルを止めた（`kill` など）場合は、その VM の検査が「エラー: 検査用シェルが応答しない」になり、
VM の起動し直し（「最初からやり直す」）を案内する。学習者は、シェルの履歴（`history`）で、手順 1 のコマンドを見られる。

**将来の改善**: イメージの inittab に ttyS1 のシェル（`ttyS1::respawn:…`）を入れれば、手順 1 が要らなくなり、
止めても自動で立ち上がる。イメージの作り直しが要るので、今回は入れていない。

### 検査の通信の扱い

- プローブの通信もキャプチャに残し、経路の列に「検査」の印を付ける（行は斜体・薄い色）。フィルタ `probe` で絞れる
- キャプチャの条件の検査（`capture`）は、プローブのポートから入ったフレームと、プローブだけに届いたフレームを除く
  （自分の検査の通信で不合格にならないように。単体テストで確かめている）
- pcap の保存は、既定で検査の通信を除く。「検査の通信も pcap に入れる」で含められる

## シナリオの JSON（`v86-link-scenario/1`）

```json
{
  "schema": "v86-link-scenario/1",
  "id": "small-office",                 // 英小文字・数字・ハイフン（32 文字まで）
  "title": "S1 小さなオフィス",
  "difficulty": "easy",                 // easy | medium | hard
  "minutes": 15,
  "summary": "一覧に出す短い説明",
  "image": "v86net",                    // 省略可。v86net だけ
  "briefing": "依頼文（小さなマークアップ）",
  "requirements": [ { "id": "R1", "text": "…", "requires": ["R2"] } ],
  "addressing": { "allowed": ["192.168.10.0/24"] },
  "switch": { "mode": "switch" },       // switch | hub
  "nodes": [ … ],
  "allow": { "addVms": 0, "removeVms": false },
  "checks": [ … ],
  "hints": [ { "level": 1, "text": "…" } ],
  "debrief": "解説",
  "feedback": "summary"                 // summary | detailed（不合格のときに見せる詳しさ）
}
```

知らない項目はエラーにする（読み飛ばさない）。文字列の長さ・配列の数には上限がある（`scenario/schema.js` の `LIMITS`）。

### 要件（requirements）

- `id` は `R1`〜`R99`。各要件に、検査が1つ以上要る
- `requires`: 前提の要件。前提が合格していなければ、その要件の検査は実行せず「未実行」にする
- 要件の結果: 検査に1つでもエラーがあれば **エラー**、不合格があれば **不合格**、全部合格なら **合格**

### アドレス（addressing）

- 使ってよいアドレスの範囲。ノード・検査に出てくる IP は、全部この中でなければならない
- そもそも許すのは、プライベートの範囲（10/8・172.16/12・192.168/16）と、**ドキュメント用の範囲**
  （192.0.2.0/24・198.51.100.0/24・203.0.113.0/24）だけ。「インターネット側」の公開アドレスは、ドキュメント用の範囲を使う
- 実在する組織の名前は使わない（依頼文・ノード名とも）

### ノード（nodes）

| 項目 | VM | プローブ | 説明 |
| --- | --- | --- | --- |
| `id` | 必須 | 必須 | 検査から参照する ID。VM ではホスト名にもなる |
| `kind` | `vm` | `probe` | |
| `role` | 必須 | 付けない | `host` / `server` / `router`（表示用） |
| `name` | 必須 | 必須 | 16 文字まで |
| `port` | 0〜7 | 8〜11 | スイッチのポート。VM は画面のスロット（P1〜P8）、プローブは画面に出ない |
| `vlan` | 省略可 | 省略可 | `{ "mode": "access", "access": 10 }` / `{ "mode": "trunk", "allowed": [10, 20], "native": 1 }`。省略は VLAN 1 のアクセス |
| `address` | 省略可 | 必須 | `IP/プレフィックス`。VM では表示用（設定は `init` で） |
| `gateway` | 省略可 | 省略可 | プローブは、別のサブネットへこのゲートウェイ経由で送る |
| `mac` | 省略可 | 必須 | `02:` で始まるローカル管理のアドレス。VM で省略すると `02:00:` ＋ IP |
| `init` | 省略可 | 付けない | 初期設定のコマンド（ttyS1 のシェルで、1つずつ実行。学習者の端末には出ない） |
| `locked` | 省略可 | ― | `true` なら閲覧のみ（端末への入力を受け付けない） |
| `note` | 省略可 | 省略可 | 表示用のメモ |

トラブルシュート型のシナリオは、`init` で **壊れた初期設定**（転送 OFF・ゲートウェイ無しなど）を入れて作る。

### 検査（checks）

共通: `id`・`requirement`（要件の ID）・`title`・`type`・`from`（検査を出すノード）・`timeoutMs`（省略時: http 8000、capture 10000、shell 15000、ほか 5000）・`failMessage`。

| `type` | 項目 | `expect` | 意味 |
| --- | --- | --- | --- |
| `ping` | `to` | `{ "reach": "success" \| "failure" }` | ping の応答が返る / 返らない |
| `tcp` | `to`・`port` | `{ "state": "open" \| "closed" }` | TCP で接続できる / できない（RST・無応答・届かない は、どれも closed） |
| `http` | `to`・`port`・`path` | `{ "status": 200, "bodyIncludes": "…" }`（どちらか以上） | HTTP GET の結果 |
| `route` | ― | `{ "defaultGateway": "IP" }` | VM のデフォルトゲートウェイ（`from` は VM） |
| `ttl` | `to` | `{ "ttl": 63 }` | ping の応答の TTL（経由したルーターの数を確かめる） |
| `capture` | `stimulus`・`observe`・`durationMs` | ― | 下を参照 |
| `shell` | `command` | `{ "exitCode": 0, "outputIncludes": "…" }` | **同梱のシナリオだけ**。VM の ttyS1 で任意のコマンドを実行 |

- `from` がプローブなら JS のプローブが、VM なら ttyS1 のシェルが実行する（同じ検査の種類を、どちらからでも出せる）
- `capture`: `from` の VM から `stimulus`（`{ "action": "arp" | "ping", "target": "IP" }`）を出し、`durationMs` の間、
  そのポートから入った `observe.protocol`（`arp` / `icmp` / `broadcast` / `ipv4`）のフレームが、どのノードに届いたかを見る。
  `observe.mustNotReach`（届いてはいけないノード）・`observe.mustReach`（届くべきノード）
- 検査は1つずつ順に実行し、終わったら何も残さない（プローブの TCP は RST で閉じる。VM のコマンドは終わるまで待つ）
- 各検査は `timeoutMs` で打ち切る（アダプタが返さなければ「エラー」）
- `feedback: "detailed"` なら、不合格のときに「期待」と「観測」を表示する。`summary` なら `failMessage` だけ

### 文のマークアップ

依頼文・要件・ヒント・解説で使えるのは、段落（空行）・箇条書き（`- `）・コードブロック（` ``` `）・強調（`**…**`）・コード（`` `…` ``）だけ。
HTML は解釈しない（`<` はそのまま文字として出る）。

## シナリオの書き方（作者向け）

1. まず要件を書く。要件は「観測できる結果」で書く（「ルーターで転送を ON にする」ではなく「PC1 から社内 Web が見られる」）
2. 要件ごとに、学習者の VM からの検査と、プローブからの検査を組み合わせる。プローブは学習者の VM の細工の影響を受けにくい
3. 「遮断されている」ことを確かめる検査（`failure`・`closed`）は、それだけでは何もしなくても合格してしまう。
   `requires` で「通るべきものが通る」要件を前提にする（S2 の R3 は R2 が前提）
4. `init` は、学習者の端末には出ない。初期状態の説明は依頼文に書く
5. 単体テスト（`node --test toys/v86-link/test/scenario.test.mjs`）で、同梱のシナリオが検証に通ることを確かめる。
   模範解答・途中の解答は `test/scenario-answers/answers.cjs` に書き、結合テストで確かめる

## セキュリティ

- **シナリオの JSON は信用できない入力として扱う。** スキーマの検証を必ず通し、検証に失敗したら読み込まない
  （エラーを表示し、いまの構成はそのまま）。大きさは 200KB まで
- **DOM への表示は textContent と、上の小さなマークアップの変換（createElement＋textContent）だけ。innerHTML は使わない。**
  ゲストの出力（検査の結果の文を含む）も同じ
- **検査の種類は型で限定する。** 任意のシェルコマンドを実行する `shell` は、同梱のシナリオ（`scenarios/index.json` に載っているもの）
  だけで有効。ファイルから読み込んだシナリオでは、検証で拒否する（`validateScenario(json, { trusted: false })`）
- 検査のコマンドに入れる値（IP・ポート・パス）は、スキーマで形を検証したものだけ。`vmshell.js` でも形を確かめ、違えば実行しない
- `init` は、読み込んだシナリオでも使える。実行されるのはエミュレータの中のゲスト（ページの外には出られない）だけ
- 仮想スイッチ・プローブに、外部（ページの外）への出口は無い。プローブはスイッチのポートにつながった JS のノードで、
  ページの外へ通信しない（「ページの外へ通信が出ない」の自動テストは維持している）。CDN などの外部通信は無い。CSP は変えていない
- プローブは、不正なフレーム・想定外の応答で例外を投げない（無視して数える）。返事が無ければタイムアウトで終わる

## 埋め込み・配布について（考え）

- 同じ仕組みで、授業用に別のシナリオ集を配れる（`scenarios/` に JSON を足し、`index.json` に載せる）。
  `index.json` に載せたものは trusted になるので、`shell` の検査を使うシナリオは、内容を確かめてから載せる
- ほかのページへの埋め込み（iframe）は、v86 の重さ（VM 1台あたり 64MB 程度）と CSP を考えると、同じオリジンで配るのがよい
- 採点（成績）に使うなら、ブラウザの中の判定は信用できない。サーバー側で同じ検査をやり直す必要がある（このおもちゃの範囲外）

## 既知の制約

- 学習者が追加した VM（`allow.addVms`）は、検査の対象にできない（シナリオの `nodes` に無いため）
- `tcp` の検査を VM から出すと、BusyBox の `nc -z` では「断られた」と「返事が無い」を区別できない（どちらも closed）
- 検査の通信（プローブ）は、学習者の VM の ARP テーブルにプローブの MAC を残すことがある
- ttyS1 のシェルは、学習者がそのまま使うこともできる（`echo … > /dev/ttyS1` など）。自習向けなので防がない
