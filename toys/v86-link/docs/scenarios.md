# シナリオ（要件から設計・構築して検証する）

依頼文と要件を読み、学習者がネットワークを設計・設定して、「検査する」で受け入れテストを実行する仕組み。
検査の方式を選んだ調査は [scenario-step0.md](scenario-step0.md)。

> **自習向けの自動判定で、不正を防ぐ仕組みではない。** 学習者は自分の VM の中で何でもできる（検査用のシェルを止める・
> 出力を細工するなど）。そのため、検査の多くは **外部からの検査（プローブ）** でも確かめている。
> 外部からの検査（プローブ）は、学習者の VM の細工の影響を受けにくい（VM の外、スイッチのポートにつないだ JS のノードが、
> 実際にパケットを送って返事を見るため）。それでも、ページの JavaScript を書き換えれば何でも「合格」にできる。

## 使い方

- 画面上の「シナリオ」から選ぶか、URL に `?scenario=small-office` のように付けて開く
- 「ファイル…」で、手元のシナリオの JSON を読み込める（信用できない入力として扱う。下の「セキュリティ」）
- 開くと、構成を作り、VM を起動して、初期設定を入れる（数十秒）。終わると端末を学習者に渡す
- 「検査する」で、全部の検査を1つずつ実行し、要件ごとに **合格 / 不合格 / 未実行 / エラー** を表示する
- 「最初からやり直す」で、VM・プローブ・スイッチの設定を全部作り直す（MAC テーブル・キャプチャも空にする）
- 「ヒントを見る」で、ヒントを段階ごとに1つずつ表示する。全部合格すると解説（debrief）が読める
- 「検査の通信を見る」で、キャプチャを検査の通信（`probe`）だけに絞る
- パケットキャプチャは **記録中が既定**（自由構成と同じ）。シナリオを開く・「最初からやり直す」と、記録を空にして記録中に戻す
  （「記録を止める」を押していても戻す。自動で止めることはない）
- シナリオを選ぶのをやめる（「なし」）と、ページを読み直して自由構成に戻る

**シナリオモードは、新しいイメージ（v86net）だけで動く**（ttyS1・iptables・8021q・httpd などを使うため）。
`?image=…` で以前のイメージを選んでいると、その旨を画面に表示して、構成を作らない。

## 同梱のシナリオ

| ID | 題 | 難易度 | 内容 |
| --- | --- | --- | --- |
| `small-office` | S1 小さなオフィス | 易 | 2つのサブネット＋ルーター。社員 PC にゲートウェイが無く、ルーターの転送が OFF（壊れた初期設定から直す、トラブルシュート型） |
| `dept-vlan` | S2 部署分離 | 中 | 1台のスイッチを VLAN 10/20 に分け、ルーターの iptables（FORWARD）で、営業 → 開発の Web（80番）だけを通す。ブロードキャストの分離はキャプチャの条件で確かめる |
| `web-publish` | S3 Webサービスの公開 | 中〜難（`hard`） | 社内・DMZ・外部の3ゾーン。DNAT で公開し、MASQUERADE で社内から外へ、FORWARD の方針 DROP ＋ conntrack で守る。外部に試験用端末 INET（検査には使わない）がある |
| `find-cause` | S4 つながらない原因を探す | 中 | トラブルシュート型。ゲートウェイ違い・転送 OFF・80番を落とすルールの3つを、層ごとに切り分けて直す（22番を止めるルールは残す） |
| `arp-spoof` | S5 社内の盗聴を止める | 中 | 同じ LAN の不明な機器 X（攻撃者ノード）が、PC1 とルーターの ARP を汚染して中間者になり、社内 Web の Basic 認証を盗んでいる。X は外せない。静的 ARP か ARP のフィルタで、行きと戻りの両方を守る |
| `switch-dai` | S6 スイッチで盗聴を防ぐ | 中 | S5 の続き。端末に固定の設定を入れずに、スイッチの DAI（有効にする VLAN・バインディング表・trusted）で X の偽の ARP を捨てる。DAI は汚染済みの ARP キャッシュを消さないので、キャッシュも消す |

**模範解答は `test/scenario-answers/` にあるため、自習するときは見ない。**（公開のディレクトリ `scenarios/` には置いていない）

## 仕組み

```
scenarios/*.json ──▶ scenario/schema.js（検証。通らなければ読み込まない）
                          │
                          ▼
scenarioui.js（画面・構成の作成・アダプタ）
   │  VM: main.js の createMachine / bootMachine（ttyS0 = 学習者の端末、ttyS1 = 検査用のシェル）
   │  プローブ: probe.js（スイッチの P9〜P12 につなぐ JS のノード。画面には出さない）
   ▼
scenario/evaluate.js（検査を1つずつ実行して判定。DOM・v86 に依存しない）
   ├─ probe アダプタ   … probe.js（ping・TCP 接続・HTTP GET を、JS がパケットを組み立てて行う）
   ├─ vm アダプタ      … vmshell.js（ttyS1 のシェルで ping・nc・wget・ip route を実行して出力を解析）
   └─ capture アダプタ … scenario/observe.js（スイッチの onFrame を検査の間だけ集める）
```

- 読み込み・検証・判定は純粋なモジュール（DOM も v86 も使わない）で、Node の単体テストで確かめている
- 検査の実行層はアダプタで差し替えられる（単体テストでは偽のアダプタ、結合テストでは本物）
- VmNode・スイッチ・キャプチャは壊していない（足したのは、2本目のシリアル `uart1` と、キャプチャの記録の `probe` の印だけ）

### 検査用のシェル（ttyS1）

学習者の端末（ttyS0）と衝突しないよう、検査のコマンドは2本目のシリアル（ttyS1）のシェルで実行する。

1. シナリオの起動中、学習者に端末を渡す前に、ttyS0 で **1回だけ** 次を実行して ttyS1 にシェルを起動する
   ```
   (setsid sh -c 'stty -echo </dev/ttyS1; PS1= PS2= exec /bin/sh </dev/ttyS1 >/dev/ttyS1 2>&1' &)
   ```
2. シナリオの初期設定（`init`）は ttyS1 で実行する（学習者の端末に出さない）
3. 端末の表示をクリアして、学習者に渡す
4. 検査のコマンドは ttyS1 だけに送る。**ttyS0 には検査のコマンドを入れない**

**スナップショット起動**（README の「動き」、`snapshot.js`）: シナリオの最初の 1 台は上の手順 1 のあと、ttyS1 のシェルが応答した時点で
`save_state` し、シナリオ用のテンプレートにする（ホスト名・MAC・`init` の前）。ほかの VM と「最初からやり直す」はそこから復元し、
手順 1 を飛ばして、ttyS1 でホスト名・MAC の設定（先頭で乱数を混ぜ、時計を合わせる）と `init` だけを実行する。
MAC を設定するまで、その VM のポートから入ったフレームは捨てる（全台が同じ ne2k の MAC で起きるため）。
復元した VM の ttyS1 のシェルが応答しなければ、テンプレートを捨てて、その VM を通常の起動でやり直す。

学習者が ttyS1 のシェルを止めた（`kill` など）場合は、その VM の検査が「エラー: 検査用シェルが応答しない」になり、
VM の起動し直し（「最初からやり直す」）を案内する。学習者は、シェルの履歴（`history`）で、手順 1 のコマンドを見られる。

**将来の改善**: イメージの inittab に ttyS1 のシェル（`ttyS1::respawn:…`）を入れれば、手順 1 が要らなくなり、
止めても自動で立ち上がる。イメージの作り直しが要るので、今回は入れていない。

### 検査の通信の扱い

- プローブの通信もキャプチャに残し、経路の列に「検査」の印を付ける（行は斜体・薄い色）。フィルタ `probe` で絞れる
- キャプチャの条件の検査（`capture`）は、プローブのポートから入ったフレームと、プローブだけに届いたフレームを除く
  （自分の検査の通信で不合格にならないように。単体テストで確かめている）
- pcap の保存は、既定で検査の通信を除く。「検査の通信も pcap に入れる」で含められる
- 攻撃者ノード（下の「攻撃者ノード」）の通信は、検査の通信として扱わない（印を付けず、`capture` の検査でも除かない）。
  攻撃者のポートを `observe.mustNotReach` に書いて、「攻撃者に届かない」を判定するため

### 攻撃者ノード（`kind: "attacker"`。`attacker.js`）

ARP スプーフィングで中間者になる JS のノード。プローブと同じく、スイッチの P9〜P12 につなぐ（学習者は端末を持たない）。シナリオ S5 で使う。

- 動き始めるのは、全部の VM の初期設定が終わってから。まず標的（`attack.targets` の 2 つの IP）それぞれの本当の MAC を ARP で調べる
- `intervalMs` ごとに、各標的へ「もう一方の IP は自分の MAC」という ARP 応答（op=2、ユニキャスト）を送り続ける。
  学習者が ARP キャッシュを消しても、すぐにまた汚染される（本物の arpspoof と同じ）
- `relay`: 自分の MAC 宛てで、IP の宛先が自分でないフレームは、宛先の本当の MAC に書き換えて送り返す（通信は切れないので、気づきにくい）。
  宛先が標的ならその標的へ、そうでなく送り元が標的なら、もう一方の標的（ゲートウェイ）へ。`decrementTtl` なら TTL を 1 減らし、
  IP ヘッダのチェックサムを計算し直す（Linux の ip_forward で中継したときと同じ。ping の TTL が 1 減るのが手がかりになる）
- 盗んだもの（loot）: 中継した TCP のデータから、HTTP のリクエスト行と `Authorization: Basic` を取り出し、デコードしたユーザー名とパスワード・
  時刻・送り元を記録する（50 件まで。新しいものを残す）。`attack.showLoot` なら、シナリオの画面に「**攻撃者が見たもの**」として新しい順に出す（textContent だけ）
- 自分の IP への ARP の問い合わせと ping には答える（ふつうのホストのふり）
- トポロジー図には、空いているスロットの位置に、`name` と `attack.label`（既定「不明な機器」）で出す。キャプチャの経路・シーケンスのレーンには `name` で出る
- 「最初からやり直す」では、タイマーを止めてからポートを外す（古い攻撃者の ARP が残らない）
- キャプチャには、ARP の送り元の IP が前と別の MAC で来たフレームに注記を付ける（Wireshark の duplicate use of IP に当たる）。
  一覧の概要に「⚠ … が別の MAC で来た」、詳細に「注記」。フィルタ `arp-dup` で絞れる

## シナリオの JSON（`v86-link-scenario/1`）

```json
{
  "schema": "v86-link-scenario/1",
  "id": "small-office",                 // 英小文字・数字・ハイフン（32 文字まで）
  "title": "S1 小さなオフィス",
  "difficulty": "easy",                 // easy | medium | hard
  "minutes": 15,
  "summary": "一覧に出す短い説明",
  "image": "v86net",                    // 省略可。v86net だけ
  "briefing": "依頼文（小さなマークアップ）",
  "requirements": [ { "id": "R1", "text": "…", "requires": ["R2"] } ],
  "addressing": { "allowed": ["192.168.10.0/24"] },
  "switch": { "mode": "switch", "locked": false },  // switch | hub。locked: true なら学習者は L2 を変えられない
  "nodes": [ … ],
  "allow": { "addVms": 0, "removeVms": false },
  "checks": [ … ],
  "hints": [ { "level": 1, "text": "…" } ],
  "debrief": "解説",
  "feedback": "summary"                 // summary | detailed（不合格のときに見せる詳しさ）
}
```

知らない項目はエラーにする（読み飛ばさない）。文字列の長さ・配列の数には上限がある（`scenario/schema.js` の `LIMITS`）。

### 要件（requirements）

- `id` は `R1`〜`R99`。各要件に、検査が1つ以上要る
- `requires`: 前提の要件。前提が合格していなければ、その要件の検査は実行せず「未実行」にする
- 要件の結果: 検査に1つでもエラーがあれば **エラー**、不合格があれば **不合格**、全部合格なら **合格**

### アドレス（addressing）

- 使ってよいアドレスの範囲。ノード・検査に出てくる IP は、全部この中でなければならない
- そもそも許すのは、プライベートの範囲（10/8・172.16/12・192.168/16）と、**ドキュメント用の範囲**
  （192.0.2.0/24・198.51.100.0/24・203.0.113.0/24）だけ。「インターネット側」の公開アドレスは、ドキュメント用の範囲を使う
- 実在する組織の名前は使わない（依頼文・ノード名とも）

### ノード（nodes）

| 項目 | VM | プローブ | 説明 |
| --- | --- | --- | --- |
| `id` | 必須 | 必須 | 検査から参照する ID。VM ではホスト名にもなる |
| `kind` | `vm` | `probe` | |
| `role` | 必須 | 付けない | `host` / `server` / `router`（表示用） |
| `name` | 必須 | 必須 | 16 文字まで |
| `port` | 0〜7 | 8〜11 | スイッチのポート。VM は画面のスロット（P1〜P8）、プローブは画面に出ない |
| `vlan` | 省略可 | 省略可 | `{ "mode": "access", "access": 10 }` / `{ "mode": "trunk", "allowed": [10, 20], "native": 1 }`。省略は VLAN 1 のアクセス |
| `address` | 省略可 | 必須 | `IP/プレフィックス`。VM では表示用（設定は `init` で） |
| `gateway` | 省略可 | 省略可 | プローブは、別のサブネットへこのゲートウェイ経由で送る |
| `mac` | 省略可 | 必須 | `02:` で始まるローカル管理のアドレス。VM で省略すると `02:00:` ＋ IP |
| `init` | 省略可 | 付けない | 初期設定のコマンド（ttyS1 のシェルで、1つずつ実行。学習者の端末には出ない） |
| `locked` | 省略可 | ― | `true` なら閲覧のみ（端末への入力を受け付けない） |
| `testOnly` | 省略可 | ― | `true` なら **学習者の試験用の端末**。検査（合否の判定）には使えない: 検査の `from`・`listener`・`observe` にも、宛先（`to`・`stimulus.target`）・期待する送り元・ゲートウェイにも、この端末やそのアドレスを書くと検証で拒否する。カードには「試験用・検査に使わない」と出る |
| `note` | 省略可 | 省略可 | 表示用のメモ |

攻撃者（`kind: "attacker"`）は、プローブと同じく `port` 8〜11・`address`・`mac` が必須で、`role`・`init`・`gateway`・`locked`・`testOnly` は付けない。
プローブと攻撃者は合わせて 4 個まで、攻撃者は 2 個まで。`attack` で動きを決める:

| `attack` の項目 | 既定 | 説明 |
| --- | --- | --- |
| `targets` | 必須 | 標的の IP の組（2 つ。例: 社員 PC とゲートウェイ）。自分のアドレスは不可 |
| `intervalMs` | 1500 | 汚染の ARP を送る間隔（200〜60000） |
| `relay` | `true` | 中継するか（`false` なら、自分あてに来たフレームを捨てる = 通信が切れる） |
| `decrementTtl` | `true` | 中継するときに TTL を 1 減らすか |
| `showLoot` | `false` | 「攻撃者が見たもの」を画面に出すか |
| `label` | `不明な機器` | トポロジー図での表示（24 文字まで） |

攻撃者は、検査の `from`・`listener` には使えない（検証で拒否する）。`observe.mustReach`・`mustNotReach`・`fromNode` には書ける。

トラブルシュート型のシナリオは、`init` で **壊れた初期設定**（転送 OFF・ゲートウェイ無しなど）を入れて作る。

### 検査（checks）

共通: `id`・`requirement`（要件の ID）・`title`・`type`・`from`（検査を出すノード）・`timeoutMs`（省略時: http 8000、capture 10000、tcp_source 8000、shell 15000、ほか 5000）・`failMessage`。

| `type` | 項目 | `expect` | 意味 |
| --- | --- | --- | --- |
| `ping` | `to` | `{ "reach": "success" \| "failure" }` | ping の応答が返る / 返らない |
| `tcp` | `to`・`port` | `{ "state": "open" \| "not_open" }` | TCP で接続できる / できない。`not_open` は、RST（断られた）・無応答（落とされた）・届かない のどれでも合格。`closed` は以前の名前で、意味は `not_open` と同じ（互換のため残している） |
| `http` | `to`・`port`・`path` | `{ "status": 200, "bodyIncludes": "…" }`（どちらか以上） | HTTP GET の結果 |
| `route` | ― | `{ "defaultGateway": "IP" }` | VM のデフォルトゲートウェイ（`from` は VM） |
| `ttl` | `to` | `{ "ttl": 63 }` | ping の応答の TTL（経由したルーターの数を確かめる） |
| `capture` | `stimulus`・`observe`・`durationMs` | ― | 下を参照 |
| `tcp_source` | `listener`・`port` | `{ "sourceIp": "IP" }` | `from` の VM から、プローブ（`listener`）の `port` へ TCP で接続し、プローブが受けた接続の **送り元 IP** を見る（NAT の確認）。下を参照 |
| `shell` | `command` | `{ "exitCode": 0, "outputIncludes": "…" }` | **同梱のシナリオだけ**。VM の ttyS1 で任意のコマンドを実行 |

- `from` がプローブなら JS のプローブが、VM なら ttyS1 のシェルが実行する（同じ検査の種類を、どちらからでも出せる）
- `capture`: `from` の VM から `stimulus`（`{ "action": "arp" | "ping", "target": "IP" }`）を出し、`durationMs` の間、
  そのポートから入った `observe.protocol`（`arp` / `icmp` / `broadcast` / `ipv4`）のフレームが、どのノードに届いたかを見る。
  `observe.mustNotReach`（届いてはいけないノード）・`observe.mustReach`（届くべきノード）。
  `observe.fromNode`（省略時は `from`）で、見るフレームの入口を変えられる（例: きっかけは PC1 からの ping だが、見るのはルーターの
  ポートから入った ICMP = 戻りの向き）。プローブは書けない。`observe.ignoreFlood: true` なら、フラッディング・ブロードキャスト・ハブで
  届いたフレームは数えない（MAC テーブルが空だったために、たまたま攻撃者のポートにも届いただけのフレームで不合格にしないため）
- `tcp_source`: プローブが `port` で待ち受け（サーバー側になる）、`from` の VM が ttyS1 で `echo … | nc -w N <プローブの IP> <port>` を実行する。
  プローブは、届いた接続の送り元 IP を記録して（データを受け取り、FIN で閉じる）、検査が終わると待ち受けをやめる（残った接続は RST）。
  接続が届かなければ不合格（「接続が届かなかった」）。送り元が混ざっていても不合格。
  例: 社内 PC から外部のホストへの接続が、ルーターの外側のアドレスから来たように見えるか（MASQUERADE / SNAT）
- プローブは、待ち受けていないポートへの SYN には RST を返す（ふつうのホストと同じ）
- 検査は1つずつ順に実行し、終わったら何も残さない（プローブの TCP は RST で閉じる。VM のコマンドは終わるまで待つ）
- 各検査は `timeoutMs` で打ち切る（アダプタが返さなければ「エラー」）
- `feedback: "detailed"` なら、不合格のときに「期待」と「観測」を表示する。`summary` なら `failMessage` だけ
- `capture` の `observe.mustBeDropped`（S6）: `arp-inspection` / `arp-src-mac` / `arp-malformed`（スイッチの DAI の理由）。`durationMs` の間に `fromNode` から入った
  `protocol` のフレームが **1 件以上あり、すべてその理由で捨てられていれば** 合格。1 件も来なければ不合格（「観測できなかった」）。`mustNotReach`・`mustReach` と一緒にも書ける

#### スイッチ（switch）

| 項目 | 既定 | 説明 |
| --- | --- | --- |
| `mode` | `switch` | `switch` / `hub` |
| `locked` | `false` | `true` なら、学習者はスイッチ（モード・ケーブル・ポートの VLAN）を変えられない |
| `allow.dai` | `false` | `true` なら、`locked` でも DAI（有効にする VLAN・バインディング表・trusted）だけは変えられる（S6） |
| `dai` | 無効 | 初期の DAI の設定（README の「DAI」）: `vlans`（有効にする VLAN）・`bindings`（`{ vlan, ip, mac }`。アドレスは `addressing.allowed` の中）・`srcMacCheck`（既定 `true`）・`trusted`（trusted にするノードの ID）。「最初からやり直す」で、この設定に戻り、数も消える |

検査用のプローブのポートは、DAI で自動的に trusted（検査の通信を捨てない）。攻撃者ノードのポートは、`dai.trusted` に書かない限り untrusted。

#### スキーマの版と互換

S3〜S6 で足したもの（`tcp` の `not_open`・`tcp_source`・`listener`・`switch.locked`・ノードの `testOnly`・`kind: "attacker"` と `attack`・
`observe.fromNode`・`observe.ignoreFlood`・`observe.mustBeDropped`・`switch.allow.dai`・`switch.dai`）は、どれも **足しただけ** で、
以前のシナリオ（S1・S2 や、`closed` を使う外部のシナリオ）はそのまま検証に通り、同じように判定される。そのため版は `v86-link-scenario/1` のまま。
新しい項目を使ったシナリオを、以前の版のページで開くと、「知らない項目・知らない検査の種類」として検証で拒否される（黙って読み飛ばさない）。

## シナリオの書き方（作者向け）

1. まず要件を書く。要件は「観測できる結果」で書く（「ルーターで転送を ON にする」ではなく「PC1 から社内 Web が見られる」）
2. 要件ごとに、学習者の VM からの検査と、プローブからの検査を組み合わせる。プローブは学習者の VM の細工の影響を受けにくい
3. 「遮断されている」ことを確かめる検査（`failure`・`not_open`）は、それだけでは何もしなくても合格してしまう。
   `requires` で「通るべきものが通る」要件を前提にするか（S2 の R3 は R2 が前提）、同じ要件の中に「通るべきもの」の検査を入れる（S3 の R4）
4. 「近道」（`iptables -F` で全部消す・方針を ACCEPT にする など）で、ほかの要件が不合格になるように、守る側の検査を入れる（S3 の R2・R4、S4 の R2）
5. L2（VLAN）を学ぶシナリオでなければ、`switch.locked: true` にして、学習者がスイッチを変えられないようにする（S3・S4）
6. `init` は、学習者の端末には出ない。初期状態の説明は依頼文に書く。ゲストの `lo`（ループバック）は既定で down なので、`ifconfig lo up` を入れておく
7. 単体テスト（`node --test toys/v86-link/test/scenario.test.mjs`）で、同梱のシナリオが検証に通ることを確かめる。
   模範解答・途中の解答は `test/scenario-answers/answers.cjs` に書き、結合テストで確かめる

## S3〜S6 の設計

### S3 Webサービスの公開（何を学ばせるか・検査の工夫）

- 学ぶこと: DNAT（公開）と FORWARD の許可は別もの / MASQUERADE（社内から外へ）/ 方針 DROP と conntrack（戻りの通信）/ DMZ を分ける意味
- ゾーン分け: S2 と同じ方式（1台のスイッチの VLAN 10・20・30 と、ルーターのトランク・ゲストの `eth0.10`・`eth0.20`・`eth0.30`）。
  ルーターは、ゲストの 8021q でタグを付け外しする（S2 と同じ。自由構成の JS の VlanLink は使わない）。L2 は `switch.locked` で固定し、学習者は iptables だけに集中する
- 外部（インターネット側）は、ドキュメント用の `203.0.113.0/24`。外部のホストはプローブ（`203.0.113.50`、ゲートウェイはルーターの外側 `203.0.113.1`）
- R1: 外部のプローブから `http://203.0.113.1/` を取得し、DMZ の Web の識別用の文字列を確かめる
- R2: 外部のプローブから、外側のアドレスの 22番・DMZ の `10.0.20.80` の 22番が `not_open`、社内の `10.0.10.11` への ping が届かない。
  外部の機器が内側のアドレスあてに直接送る場合も確かめる（プローブのゲートウェイをルーターにしている）。
  社内あては TCP の 80番ではなく ping で見る: DNAT を `-i eth0.30 --dport 80` だけで書くと（`-d` なし）、社内あての 80番も DMZ の Web に書き換わり、
  「社内に届いた」ように見えてしまう（実際は DMZ が答えている）。結合テストで見つけて直した。
  こうしないと、DNAT が 80番だけなら、FORWARD の方針が ACCEPT でも R2 が合格してしまう。R1 を前提にする（全部止めて合格させない）
- R3: 社内 PC から DMZ の Web・外部への ping と、`tcp_source`（外部のホストから見た送り元が `203.0.113.1`）。
  MASQUERADE が無くても、プローブがルーター経由で返事をするので ping は通る。送り元の検査だけが NAT の有無を見分ける
- R4: DMZ のサーバー（閲覧のみの VM の ttyS1）から社内 PC の 80番（社内 PC で httpd が待ち受けているので、「待ち受けなし」で合格にはならない）が `not_open`。
  同じ要件に「社内 PC から DMZ の Web が取れる（戻りの通信が通る）」を入れて、全部止めて合格させない
- 近道の防ぎ方: 方針 ACCEPT ＋ `iptables -F FORWARD` → R2・R4 が不合格。方針 DROP のまま `iptables -F` → R1・R3・R4 が不合格（結合テストで確かめている）
- 外部の試験用端末 **INET**（`203.0.113.60`、VLAN 30、ゲートウェイ `203.0.113.1`、`testOnly`）: 学習者が、外から見た動き（`wget http://203.0.113.1/`・`nc -z`・tcpdump）を自分で確かめるための VM。
  **検査には使わない**（スキーマの `testOnly` で、検査から参照できないようにしている）。理由: 学習者が操作できる端末なので、そこで通ったことを合格の条件にすると、
  INET の側の設定（経路の追加など）や、主旨から外れたルーターの設定（例: DNAT を書かずに方針 ACCEPT のままにして、INET から DMZ のアドレスへ直接届く）で合格できてしまう。
  依頼文に「正しく設定できたかを確かめるための端末で、合否の判定には使わない。INET の設定は変えずに試す」と注釈を付けた。
  結合テストで、転送だけの状態で INET から DMZ に直接届いても R1 が不合格のままであることを確かめている。VM は4台になる（メモリ約 200MB 増）
- 任意の要件（LOG）は入れなかった: 要件にすると「全部合格」に要る作業が増え、目安の時間（25分）を超えやすい。解説の「発展」で `-j LOG` と `dmesg` を紹介している
- 任意のキャプチャ条件（外部からの 22番の SYN が DMZ に現れない）は入れなかった: この構成では、22番の SYN が DMZ に出ていく設定なら、R2 の `not_open` の検査が先に不合格になる（同じことを2回見る）。
  キャプチャの条件は、検査の通信（プローブが入ったポートのフレーム）を除くが、ルーターが転送したフレームは除かないので、作るなら `stimulus` をプローブから出す拡張が要る

### S4 つながらない原因を探す（何を学ばせるか・検査の工夫）

- 学ぶこと: 層ごとの切り分け（L2 → L3 → L4）と、`tcpdump`・キャプチャ・`iptables -L -v` で「どこまで届いているか」を見ること / セキュリティのルールを残して直すこと
- 不具合は3つで、1つ直すと次に止まる場所が見える順になっている:
  PC1 のゲートウェイ違い（`192.168.50.254`。ARP の問い合わせに答えが無い）→ ルーターの転送 OFF（`eth0.10` には届くが `eth0.20` に出ない）→
  80番を落とす「一時的な保守」のルール（ping は通るが Web だけ届かない。SYN が繰り返される）
- 残すべきルール（社員 LAN → 22番の DROP）にも、消すべきルールにも、`-m comment` で説明を付けた（`iptables -L` で見える。手がかりになる）
- R1 は PC1 と、社員 LAN のプローブ（PC1 以外の社員の PC）の両方から。PC1 だけを特別扱いする直し方では合格しない
- R2（22番の遮断）は R1 を前提にする。`iptables -F` で全部消すと R1 は合格し、R2 が不合格になる
- ゲートウェイの不具合は「サブネットマスク」ではなく「ゲートウェイ」を選んだ: マスクを `/16` にすると、同じ VLAN の中では ARP に答える相手がいないだけで、
  ゲートウェイ違いと見え方がほぼ同じになる。ゲートウェイ違いのほうが、依頼文のアドレス計画と見比べて見つけやすい
- tcpdump・キャプチャは、依頼文とヒント1・2で促し、解説に「各不具合が、キャプチャでどう見えるか」を書いた

### S5 社内の盗聴を止める（何を学ばせるか・検査の工夫）

- 学ぶこと: ARP には認証が無い / スイッチの LAN でも中間者攻撃で盗聴できる（ハブでなくても）/ 静的 ARP・ARP のフィルタで守る /
  片方向だけ守っても足りない / TTL や `ip neigh`・キャプチャで異常に気づく / 本物の対策（DAI・802.1X・HTTPS）と Basic 認証が平文であること
- 構成は S1 と同じ（VLAN なし・1 台のスイッチ。`switch.locked`）に、攻撃者ノード X（P10、`192.168.10.66`）を足した。
  X は PC1 とルーターの両方を汚染し、中継する（`relay`・`decrementTtl`）ので、通信は切れない。PC1 の `init` で、業務アプリの代わりに
  「5 秒ごとに `wget http://staff:s3cret@…/staff/`」をバックグラウンドで動かし、SV の BusyBox httpd は `/staff` に Basic 認証（`httpd.conf`）を掛けた
- 要件と検査:
  - R1: PC1 と社員 LAN のプローブから社内 Web が見られる（http）。通信を止める対策（ARP を全部落とす）はここで不合格
  - R2（R1 が前提）: PC1 のポートから入った IPv4 が X に届かない（capture。`fromNode: pc1`・`ignoreFlood`）。
    **ping だけでなく IPv4 全体を、6 秒（汚染の間隔 1.5 秒の 4 倍）見る**。PC1 の 5 秒ごとの HTTP も入るので、
    検査の直前に `ip neigh flush` しただけ（すぐに汚染し直される）では合格しない
  - R3（R1 が前提）: ルーターのポートから入った IPv4 が X に届かない（capture。`fromNode: router`。きっかけは PC1 からの ping = 戻りの向き）と、
    PC1 からの ping の応答の TTL が 63（ttl）。行きの向きは TTL では分からない（ping の応答は戻りの向きを通る）ので、TTL の検査は R3 に置いた。
    R が汚染されていると、応答が X を経由して 62 になる
  - `ignoreFlood` は、MAC テーブルが空だったなどで、たまたま X のポートにもフラッディングされただけのフレームで不合格にしないため
- 途中の解答の結果（`test/scenario-answers/answers.cjs`。結合テストで確かめている）:
  | 解答 | R1 | R2 | R3 |
  | --- | --- | --- | --- |
  | 何もしない | 合格 | 不合格 | 不合格 |
  | PC1 だけ静的 ARP（片方向だけ） | 合格 | 合格 | 不合格 |
  | PC1 で ARP を全部落とす（nft の policy drop ＋ キャッシュを消す） | 不合格 | 未実行 | 未実行 |
  | キャッシュを消すだけ（PC1 と R） | 合格 | 不合格 | 不合格 |
  | 解答B: nft の `arp` ファミリーで、正しい MAC 以外からの `192.168.10.1` / `192.168.10.11` の ARP を落とす（両方） | 合格 | 合格 | 合格 |
  | 解答A: `ip neigh replace … nud permanent`（両方） | 合格 | 合格 | 合格 |
- v86net のカーネルで、`nft` の `arp` ファミリー・`arptables`・`ip neigh … nud permanent` が動くこと、Linux が汚染の ARP 応答で既存のエントリを書き換えること、
  静的なエントリ・ARP のフィルタでは書き換わらないことを、先に Node の v86 で確かめた（汚染中の TTL 62、対策のあと 63・中継 0）
- 依頼文には「自分の機器の MAC は、その機器の端末で調べられる」ことと「X は外せない」ことを書いた。ヒント 1 は `ip neigh` と `ip link show eth0` の見比べと TTL、
  ヒント 2 はキャプチャの `arp`（`arp-dup`）とシーケンス、ヒント 3 は `nud permanent` の書き方と「戻りの向きも」
- 解説は、ARP に認証が無いこと・静的 ARP の運用の重さ・本物の対策（スイッチの DAI、802.1X、暗号化 = HTTPS）・Basic 認証が平文であること。
  シーケンスで「対策の前後で、PC1 → X → R が PC1 → R に戻る」のを見るよう促す
- 「攻撃者が見たもの」（`showLoot`）で、盗まれているもの（ユーザー名とパスワード）と、対策のあとは増えないことが、画面で分かる

### S6 スイッチで盗聴を防ぐ（何を学ばせるか・検査の工夫）

- 学ぶこと: DAI はスイッチが ARP を検査する / trusted と untrusted / バインディング表が無いと正規の端末も止まる /
  **DAI は新しい汚染を止めるだけで、汚染済みの ARP キャッシュは消さないと治らない**（攻撃者が中継を続けるので、通信が通る限りキャッシュは REACHABLE のまま残る）
- 構成は S5 と同じ（PC1・R・SV・X・probe-lan。PC1 の Basic 認証のループも同じ）。スイッチは `locked: true`・`allow.dai: true` で、DAI だけ変えられる。DAI は無効から始まる
- 要件と検査:
  - R1・R2・R3: S5 と同じ（Web が見られる / 行き・戻りが X を経由しない。戻りは TTL 63 も）
  - R4（R1 が前提）: capture の `mustBeDropped`。きっかけは PC1 の ARP で、見るのは X のポートから入った ARP。4 秒の間に 1 件以上あり、すべて `arp-inspection` で捨てられていれば合格。
    X は 1.5 秒ごとに汚染の ARP を出すので、4 秒あれば必ず観測できる。X のポートを trusted にする・DAI を無効にする → 不合格
  - R5（R1 が前提）: shell の検査（同梱のシナリオなので使える）で、PC1 と R に `nud permanent` のエントリが無く、nft の arp ファミリーのテーブルに規則が無いこと
    （`arptables` はこのイメージでは nftables 版なので、`arptables -A` の規則も nft の `table arp filter` に入る。規則の無い空のテーブル・`policy accept` だけのものは許す）。
    S5 の解答（静的 ARP・nft の ARP フィルタ）はここで不合格になる
- 依頼の案から変えたところ: 模範解答の表は「PC1 と R（192.168.10.1）」ではなく、**VLAN 1 の正規の機器すべて**（PC1・R の `192.168.10.1` と `192.168.20.1`・SV）にした。
  この構成は全部が VLAN 1 にあり、SV と R の `192.168.20.1` の間の ARP も DAI の検査を通る。PC1 と R の 1 つだけでは、SV と R の間の ARP が捨てられて R1 が不合格になる。
  別解として「表に PC1 と SV、R のポートは trusted」も模範解答に入れた（R は 2 つのアドレスを持つので、trusted が自然）
- 途中の解答の結果（`test/scenario-answers/answers.cjs`。結合テストで確かめている。どの解答も、攻撃者が汚染し終わるまで 5 秒待ってから操作する）:
  | 解答 | R1 | R2 | R3 | R4 | R5 |
  | --- | --- | --- | --- | --- | --- |
  | 何もしない | 合格 | 不合格 | 不合格 | 不合格 | 合格 |
  | DAI を有効にしたが表が空（キャッシュも消す） | 不合格 | 未実行 | 未実行 | 未実行 | 未実行 |
  | 全部のポートを trusted（X も） | 合格 | 不合格 | 不合格 | 不合格 | 合格 |
  | DAI と表は正しいが、キャッシュを消していない | 合格 | **不合格**※ | **不合格**※ | 合格 | 合格 |
  | S5 の解答（静的 ARP） | 合格 | 合格 | 合格 | 不合格 | 不合格 |
  | 表に PC1・SV、R のポートは trusted、キャッシュを消す | 合格 | 合格 | 合格 | 合格 | 合格 |
  | 表に PC1・R（2 つ）・SV、キャッシュを消す（模範解答） | 合格 | 合格 | 合格 | 合格 | 合格 |
- ※「キャッシュを消していない」: 汚染された ARP のエントリは、DAI を有効にしたあともしばらく X の MAC のまま残る（X が中継を続けるので通信は通り、エントリは REACHABLE とみなされる）。
  ただし **ずっとではない**。8 台の結合テストのうち 1 回で R2 だけが合格したので、ゲストの `ip neigh` を 5 秒ごとに見た（DAI を有効にした時点から）:

  | 時間 | PC1 から見た R | R から見た PC1 |
  | --- | --- | --- |
  | 0〜26 秒 | X の MAC・REACHABLE | X の MAC・REACHABLE |
  | 31〜36 秒（`?snapshot=off` では 41〜46 秒） | X の MAC・REACHABLE | X の MAC・STALE → DELAY |
  | 41 秒（同 51 秒） | X の MAC・REACHABLE | FAILED（X の MAC へのユニキャストの確かめに、誰も答えない） |
  | 46 秒（同 56 秒）〜 | 本物の MAC | 本物の MAC（ブロードキャストで引き直し、本物の PC1 が答える。DAI は通す） |

  R は転送するだけで、PC1 のエントリを自分の通信で確かめられないので、先に時間切れになって ARP を引き直す。その ARP の要求（送り元は本物の R）を受けて、
  PC1 のエントリも本物に戻る。Linux の時間切れは 15〜45 秒の乱数なので、検査の 18 秒の間に片方だけ治っていることがある。
  そこで結合テストでは「R2・R3 の **少なくとも 1 つ** が不合格」で確かめる（依頼では「R2・R3 が不合格」だった）。学びとしては、
  「DAI を入れても、Linux が引き直すまでの数十秒は盗み見られたまま」になり、ヒント 2・解説もそう書いた
- ヒント 1 は「DAI を有効にしたら、フィルタ `dai` で正規の機器も捨てられていないか見る」、ヒント 3 は表の書き方（R の 2 つのアドレス、または trusted）と、両方の端末の `ip neigh flush`
- 解説は、本物は DHCP snooping が表を作ること・固定の IP の機器は静的に書くか trusted・DAI を入れたあとの汚染済みのキャッシュは本物の運用でも起きること・暗号化（HTTPS）がいちばん大事なこと。
  シーケンスで、有効にする前後の ARP（X の `is at` → X のレーンの ✕）を見比べるよう促す
- 「最初からやり直す」では、DAI の設定（有効・表・trusted）と数を初期に戻す（`teardown` で `sw.dai.reset()`、`start` でシナリオの `switch.dai` を入れ直す）

## セキュリティ

- **シナリオの JSON は信用できない入力として扱う。** スキーマの検証を必ず通し、検証に失敗したら読み込まない
  （エラーを表示し、いまの構成はそのまま）。大きさは 200KB まで
- **DOM への表示は textContent と、上の小さなマークアップの変換（createElement＋textContent）だけ。innerHTML は使わない。**
  ゲストの出力（検査の結果の文を含む）も同じ
- **検査の種類は型で限定する。** 任意のシェルコマンドを実行する `shell` は、同梱のシナリオ（`scenarios/index.json` に載っているもの）
  だけで有効。ファイルから読み込んだシナリオでは、検証で拒否する（`validateScenario(json, { trusted: false })`）
- 検査のコマンドに入れる値（IP・ポート・パス）は、スキーマで形を検証したものだけ。`vmshell.js` でも形を確かめ、違えば実行しない
- `init` は、読み込んだシナリオでも使える。実行されるのはエミュレータの中のゲスト（ページの外には出られない）だけ
- 仮想スイッチ・プローブに、外部（ページの外）への出口は無い。プローブはスイッチのポートにつながった JS のノードで、
  ページの外へ通信しない（「ページの外へ通信が出ない」の自動テストは維持している）。CDN などの外部通信は無い。CSP は変えていない
- プローブは、不正なフレーム・想定外の応答で例外を投げない（無視して数える）。返事が無ければタイムアウトで終わる
- **攻撃者ノードはページの中だけで動く。** スイッチのポートにつながった JS のノードで、出すのは仮想スイッチへのフレームだけ。
  ページの外へは通信しない（外への出口が無い）。攻撃の相手は、同じページの中のエミュレータのゲストだけ。盗んだ認証情報も、
  そのページのメモリにだけあり、どこにも送らない・保存しない（リロードで消える）。不正なフレームで例外を投げず、`stop()` のあとは何も送らない

## 埋め込み・配布について（考え）

- 同じ仕組みで、授業用に別のシナリオ集を配れる（`scenarios/` に JSON を足し、`index.json` に載せる）。
  `index.json` に載せたものは trusted になるので、`shell` の検査を使うシナリオは、内容を確かめてから載せる
- ほかのページへの埋め込み（iframe）は、v86 の重さ（VM 1台あたり 64MB 程度）と CSP を考えると、同じオリジンで配るのがよい
- 採点（成績）に使うなら、ブラウザの中の判定は信用できない。サーバー側で同じ検査をやり直す必要がある（このおもちゃの範囲外）

## 既知の制約

- 学習者が追加した VM（`allow.addVms`）は、検査の対象にできない（シナリオの `nodes` に無いため）
- `tcp` の検査を VM から出すと、BusyBox の `nc -z` では「断られた」と「返事が無い」を区別できない（どちらも `not_open`）。
  「RST で断られた」と「落とされた」を区別する種類は、今は無い（プローブは区別できるが、要件の判定には使っていない）
- `tcp_source` の待ち受けはプローブだけ（VM で待ち受けて、送り元を記録する種類は無い）
- 検査の通信（プローブ）は、学習者の VM の ARP テーブルにプローブの MAC を残すことがある
- ttyS1 のシェルは、学習者がそのまま使うこともできる（`echo … > /dev/ttyS1` など）。自習向けなので防がない
