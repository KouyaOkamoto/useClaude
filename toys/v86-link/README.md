# ブラウザ内 Linux を LAN でつなぐ（v86・ハブ / スイッチ・VLAN・ルーター）

同じページの中で、エミュレータ [v86](https://github.com/copy/v86) の Linux を **2〜8台** 起動し、仮想の **ハブ / L2 スイッチ** でつなぐ。
スイッチは **VLAN（802.1Q。アクセス / トランク）** を持ち、**ルーター役の Linux VM** で複数のサブネット・VLAN の間をつなげる（router-on-a-stick）。
VM ごとのターミナルから ping・HTTP・TCP で疎通を確かめられるほか、ハブとスイッチを切り替えて
「ハブなら盗聴できるが、スイッチではできない」「MAC アドレステーブルの学習とエージング」「MAC フラッディング」、
「ゲートウェイ・ルーティング・TTL の減少」「VLAN の分離と VLAN 間ルーティング」を体験できる。
仮想スイッチを通ったフレームは記録していて、画面で一覧・詳細を見たり、pcap ファイルとしてダウンロードして Wireshark などで開いたりできる。
**すべてブラウザの中で完結していて、サーバーも外のネットワークも使わない。**

## 仕組み: フレームの橋渡し

v86 公式のサンプル [`examples/two_instances.html`](https://github.com/copy/v86/blob/master/examples/two_instances.html) と同じ方式。

1. v86 の NIC（ne2k）は、ゲストがパケットを送るたびに、Ethernet フレームを `net0-send` イベント（`Uint8Array`）で外に出す。
   `net_device` に `relay_url` を指定していないので、外のネットワークにはつながらず、フレームを出すだけになる
2. `VirtualSwitch` が、モード（ハブ / スイッチ）に従って届け先のポートを決める（下の「ハブとスイッチ」）
3. 渡された側は `emulator.bus.send("net0-receive", frame)` で、そのフレームを自分の NIC が受け取ったことにする

### VM の名前・IP・MAC

名前はスロット（= スイッチのポート番号）で決まり（P1 = A … P8 = H。ルーターは P8 の R）、IP は**所属するサブネットの中で .2 から空いているもの**、
MAC は `02:00` + IP の4バイト（重複しない）。名前や図のラベルはこのページが決めたもので、ゲストが出したホスト名などは表示に使わない。
サブネットを選ばなければ LAN0（10.5.0.0/24。以前の版と同じ）なので、A・B・C … は以前と同じ 10.5.0.2・.3・.4 …になる。

| スロット（ポート） | 名前 / ホスト名 | IP（LAN0 のとき） | MAC |
| --- | --- | --- | --- |
| P1 | A / a | 10.5.0.2/24 | 02:00:0a:05:00:02 |
| P2 | B / b | 10.5.0.3/24 | 02:00:0a:05:00:03 |
| P3 | C / c | 10.5.0.4/24 | 02:00:0a:05:00:04 |
| … | … | … | … |
| P8 | H / h、またはルーター R / r | 10.5.0.9/24（ルーターは各サブネットの .1） | 02:00:0a:05:00:09（ルーターは 02:00:0a:05:00:01） |

- **MAC はゲストの中で設定する。** v86 0.5.472 の ne2k は MAC を起動ごとにランダムに作り（`00:22:15:xx:xx:xx`。`src/ne2k.js`）、
  それを決めるオプションは無い（`v86.d.ts` にあるのは `router_mac` などで、NIC の MAC ではない）。そこで、起動してシェルが出たら、
  シリアルから次のコマンドを送る（「ネットワーク設定をやり直す」でも同じ）。MAC は「ローカル管理アドレス」（先頭が `02`）で、後ろ4バイトを IP と同じにして読みやすくした
  ```sh
  hostname a; export PS1='\h:\w% '; ifconfig eth0 down; ip addr flush dev eth0; ip neigh flush dev eth0; \
    ifconfig eth0 hw ether 02:00:0a:05:00:02 && ifconfig eth0 10.5.0.2 netmask 255.255.255.0 up && \
    route add default gw 10.5.0.1 && ip addr show eth0 | grep -E 'ether|inet ' && echo "NET""-OK"
  ```
  最後の `NET-OK` が出たら設定完了（`"NET""-OK"` と分けて書くので、コマンドのエコーでは一致しない）
- 同じサブネットの同じ IP に足し直した VM は、前の VM と同じ MAC になる。ほかの VM の ARP キャッシュが古いままでも、そのまま通じる

### 動き

1. 最初は A・B の2台（LAN0。以前の2台構成と同じ IP）。「起動」（または学習の「開始」）で、まだ起動していない全台を起動する。
   イメージ（約10MB）は1回だけダウンロードして全台で共有する。起動したら自動でホスト名・MAC・IP・ゲートウェイを設定する。
   進み具合（ダウンロード → BIOS → ブート → ネットワーク設定 → 準備完了）は、端末のカードとタブに出る
2. 「＋ VM」: 空いているスロットに VM を足し、すぐ起動してネットワーク設定まで進める（最大 8 台）
3. カードの「×」: その VM を止め（v86 の `destroy()`）、スイッチのポートを外し、そのポートで覚えた MAC を消し、カードとターミナルを捨てる
4. ポートの設定パネルの「ケーブルを抜く」・遅延（ms）・損失（%）: そのポートのケーブルの性質。フレームは送り元と届け先の2本のケーブルを通るので、
   遅延は「送り元 + 届け先」、損失は送り元で1回・届け先ごとに1回判定する
5. L2 スイッチ / ハブは、動いたまま切り替えられる

学習の手順・プリセットは、押した順に1つずつ実行する（実行中に押したものは、終わってから）。

## ハブとスイッチ

| | ハブ | L2 スイッチ（既定） |
| --- | --- | --- |
| 届け先 | 入ってきたポート**以外の全ポート**（宛先を見ない） | 宛先 MAC を知っていれば**そのポートだけ**。知らない宛先・ブロードキャスト・マルチキャスト（宛先 MAC の先頭オクテットの最下位ビットが 1）は、入ってきたポート以外の全ポート（フラッディング） |
| MAC の学習 | しない | 送り元 MAC と入ってきたポートを覚える（送り元がマルチキャストの不正なフレームは覚えない）。別のポートから来たら覚え直す |
| 同じポートへ | 返さない | 返さない。宛先が入ってきたポートの先にいるときは、どこにも届けない（`filtered`） |
| トポロジー図 | 入った線（青）と、ほかの全部の線（緑）が光る | 入った線と、宛先の線1本だけが光る（知らない宛先はフラッディングで全部） |

- **モードを切り替えると、MAC アドレステーブルは空にする**（ハブ → スイッチ、スイッチ → ハブのどちらでも）。ハブはテーブルを使わないので、
  残しておくと「スイッチに戻したら、ハブの間の古い情報で転送する」ことになり、学習の様子も見せられない。スイッチに戻したら、最初のフラッディングから学習し直す
- ポートを外したとき・ケーブルを抜いたときも、そのポートで覚えた MAC は消す
- 転送の判断（`hub` / `known` / `flood` / `broadcast` / `filtered`）は、キャプチャの詳細の「仮想スイッチ」に出る
- 壊れたフレーム（14バイトの Ethernet ヘッダより短い・バイト列でない）は、どのモードでも例外を投げず、どこにも届けず「捨てた（runt）」として記録する

### MAC アドレステーブルの仕様

| 項目 | 内容 |
| --- | --- |
| エントリ | MAC → { ポート, 最後に見た時刻 }。画面には MAC・ポート・最後に見た時刻・残り時間を出す（新しい順に 200 件まで） |
| エージング | 既定 **300 秒**（画面で 1〜3600 秒に変えられる）。最後に見てから過ぎたエントリは、検索したとき・表示するとき・テーブルがいっぱいのとき（1 秒に1回まで）に消す |
| 上限 | **1024 件** |
| 上限に達したとき | **新しい MAC は覚えない**（覚えているエントリの時刻とポートの更新は続ける）。覚えられなかった MAC が宛先のフレームは「知らない宛先」なので**フラッディング**になる。覚えられなかった回数を画面に出す |

上限に達したときの振る舞いは、ほかに「古いものを捨てて新しいものを覚える」「すべてフラッディングに切り替える」も考えたが、
本物のスイッチの CAM テーブルがあふれたときと同じ「新しいものを覚えない」にした。理由:

- 偽の MAC を大量に送られても、テーブルは 1024 件より増えず、処理は1フレームあたり Map の検索1回で済む
  （いっぱいのときの掃除も 1 秒に1回まで）。テストで 10 万個の偽 MAC を入れても 3 秒かからない
- すでに覚えている正規の端末は追い出されない。一方、覚えられなかった端末あての通信はフラッディングになり、
  **スイッチなのにほかのポートから盗聴できる**。これが MAC フラッディング攻撃の仕組みで、教材としてそのまま見せられる
  （学習用の「MAC フラッディング」）。偽のエントリはエージングで消えると、また覚えられるようになる

## 演習（学習: L2）

上の「学習」で選び、「開始」してから手順を実行する（足りない VM は足して起動する）。

1. **ハブで盗聴**: A・B・C をそろえてハブにし、C で `tcpdump -n -l -i eth0 icmp` を動かす。A から B へ ping を3回。
   ハブは全ポートへ届けるので、**C の tcpdump に A↔B の ICMP が出る**（`6 packets captured`）。キャプチャでも経路が `A → B, C` になる。
   フィルタ `icmp out:c` で「C にも届いたフレーム」だけを出せる
2. **スイッチでは盗聴できない**: スイッチにしてテーブルを空にし、A と B の ARP キャッシュを消して（`ip neigh flush dev eth0`）同じことをする。
   ARP（ブロードキャスト）のやりとりでスイッチが A と B の MAC を覚えるので、ICMP は相手のポートにしか届かず、**C の tcpdump には出ない**
   （`0 packets captured`）。キャプチャの経路は `A → B` / `B → A`
   - ARP キャッシュを消さずに、テーブルだけ空の状態で ping すると、最初の ICMP は宛先を知らないのでフラッディングになり、C に1つだけ見えることがある。これも観察のポイント
3. **MAC テーブルの観察**: スイッチでテーブルを空にし、A→B、C→A と ping する。送り元 MAC がポートと一緒に1件ずつ増え、残り時間が減っていく。
   エージングを数秒にすると、通信の無いエントリが消えるのが見える
4. **MAC フラッディング**: スイッチでテーブルを空にしたあと、C のポートから、送り元 MAC を偽ったフレームを 1100 個入れる
   （ゲストにはこれを作る道具が無いので、ページの JavaScript が C のポートに入ったことにして送る。ethertype は実験用の 0x88b5、宛先は C 自身）。
   テーブルが 1024 件で埋まり、A と B の MAC を覚えられないので、**スイッチなのに C の tcpdump に A↔B の ICMP が出る**
5. **ケーブル: B を抜く**: B のケーブルを抜いて A から ping（届かない。キャプチャは `A → ✕`）。5 秒後に差し直す。カードのチェックボックスで、どのポートでも抜ける

### promiscuous モードについて（このイメージでの確認）

`tcpdump` は既定で NIC を **promiscuous モード**にする（自分の MAC 宛てでないフレームも受け取る）。このイメージ（Buildroot・ne2k）で確かめた結果:

- C で tcpdump を動かしている間は `cat /sys/class/net/eth0/flags` が `0x1103`（`0x100` = IFF_PROMISC が立つ）。止めると `0x1003` に戻る
- ハブで `tcpdump -p`（promiscuous にしない）にすると、A↔B の ping を流しても `0 packets captured`。自分宛てでないユニキャストは、
  NIC（v86 の ne2k の受信フィルタ）かゲストのカーネルで捨てられて tcpdump に届かない（どちらで捨てているかまでは確かめていない）
- 手で切り替えるなら `ip link set eth0 promisc on`（BusyBox の `ip` で使える）

（この確認は、ブラウザではなく Node 上の v86 0.5.472 で3台をハブ相当につないで行った。ブラウザの e2e では promiscuous の tcpdump だけを使っている）

### nc と httpd が無い

v86 の公式 Linux イメージ（`linux4.iso` と `buildroot-bzimage68.bin`）は、どちらも `nc` と `httpd` を持っていない（BusyBox の applet にも無い）。
`buildroot-bzimage68.bin` には socat があるので、`nc` の代わりに `socat - TCP-LISTEN:7000` / `socat - TCP:<IP>:7000`、
`httpd` の代わりに `socat TCP-LISTEN:8080,fork EXEC:<シェルスクリプト>` を使っている。詳しくは [images/README.md](images/README.md)。

## ルーティング（L3）と VLAN

### 構成

```
  A 10.5.1.2/24 (gw 10.5.1.1)        B 10.5.2.2/24 (gw 10.5.2.1)
        │ アクセス VLAN 10                  │ アクセス VLAN 20
  ┌─────┴──────────────── L2 スイッチ（VLAN 対応）──────────┴─────┐
  └──────────────────────────────┬────────────────────────────────┘
                                 │ P8 トランク（許可 1,10,20・ネイティブ 1）… 802.1Q タグ付き
                          VlanLink（JS。タグの付け外し）
                                 │ タグなし
                     R（本物の Linux）eth0: 10.5.0.1/24・10.5.1.1/24・10.5.2.1/24、ip_forward=1
```

| サブネット | 範囲 | VLAN | ゲートウェイ |
| --- | --- | --- | --- |
| LAN0 | 10.5.0.0/24（以前の版と同じ。最初の A・B はここ） | 1 | 10.5.0.1 |
| LAN1 | 10.5.1.0/24 | 10 | 10.5.1.1 |
| LAN2 | 10.5.2.0/24 | 20 | 10.5.2.1 |

- ホストは、追加するとき（「所属」）と、カードのサブネットの選択で所属を変えられる。IP は**サブネットごとに .2 から空いているもの**、
  MAC は `02:00` + IP の4バイト（例 10.5.1.2 → 02:00:0a:05:01:02）、デフォルトゲートウェイはそのサブネットの .1 を自動で設定する
  （`route add default gw …`。ルーターがまだ無くても設定しておく）
- ルーター R は「＋ ルーターを追加」か、ルーティングの学習用ボタンで P8 に置く（1台だけ）。起動したら次を自動で設定する
  ```sh
  ifconfig eth0 hw ether 02:00:0a:05:00:01 && ifconfig eth0 10.5.0.1 netmask 255.255.255.0 up && \
    ip addr add 10.5.1.1/24 dev eth0 && ip addr add 10.5.2.1/24 dev eth0 && \
    sysctl -q -w net.ipv4.ip_forward=1 net.ipv4.conf.all.send_redirects=0 net.ipv4.conf.eth0.send_redirects=0
  ```
  同じ eth0 で受けて同じ eth0 へ出すので、Linux が ICMP redirect（「直接送れ」）を送らないよう `send_redirects=0` にしている
- 「サブネットごとに VLAN を分ける」（既定 ON）: ホストのポートはアクセス（サブネットの VLAN）、R のポートはトランク（1・10・20 を許可、ネイティブ 1）。
  OFF にすると、全ポートがアクセス VLAN 1 になり、3つのサブネットが1つの L2 に同居する（それでも、別のサブネットへはゲートウェイを通る）
- 画面の「ルーター」パネルに、ゲストの `ip route` と `ip_forward` を読んで、**テキストとして**表示する（「ルーティングテーブルを読む」「転送 ON / OFF」）

### ルーターの方式（ステップ0の調査の結果。詳しくは [docs/step0-routing-vlan.md](docs/step0-routing-vlan.md)）

依頼の優先は「ルーターを本物の Linux にし、NIC 2枚か、router-on-a-stick（ゲストの `eth0.10` / `eth0.20`）で作る」だったが、調べると:

- **v86 は1台の VM に NIC を1枚しか持たせられない**（`net_device` は1つ。v86 の中で ne2k を1つだけ作る）
- **ゲストのカーネルに 8021q が無い**（`ip link add … type vlan` も `vconfig` も `Operation not supported`。モジュールも無い）。
  v86 が配っているほかの小さなイメージ（Linux 5.6・4.16）も同じ。`iptables` も無い。`ip_forward`・1枚の NIC に複数の IP・`traceroute`・`tcpdump` はある
- ゲストの NIC は、タグ付きフレームを 1518 バイトまでそのまま受け取れる（`tcpdump -e` で見えた）が、ゲストはタグを作れない

そこで、**ルーターは本物の Linux のまま**（ルーティングテーブル・TTL の減少・ICMP time exceeded・`ip_forward`・ゲートウェイはすべてゲストの Linux）にし、
**タグの付け外しだけを、ルーターの NIC とスイッチの間の JavaScript（`VlanLink`）が代わりに行う**方式にした（依頼者に確認して決定）。

| 方向 | VlanLink がすること |
| --- | --- |
| スイッチ → R | トランクから来たタグ付きフレームのタグを外して、R の eth0 に渡す |
| R → スイッチ | 宛先の IP（ARP なら問い合わせ・答えの相手の IP）が、どのサブネットかで VLAN を決めてタグを付ける。ネイティブ VLAN（1）のサブネットあてと、どのサブネットでもないもの（IPv6・255.255.255.255 など）はタグなし |

- 本物の router-on-a-stick との違い: 本物は「どのサブインターフェース（eth0.10 / eth0.20）から出すか」でタグが決まる。
  ここでは「宛先の IP のサブネット」で決める（R の各サブネットのアドレスは、すべて eth0 にある）。
  ルーターの IP の設定で `eth0.10` のようなサブインターフェースを作る練習はできない
- スイッチとトランクの上のフレームは、本物の 802.1Q のタグ付き（キャプチャ・pcap で見える）
- JS の仮想ルーター（次点の案）は作っていない。ゲストの Linux で `ip route`・`ip_forward`・`route add default gw` を触れることを優先した

### VLAN の仕様（`switch.js`）

| 項目 | 動き |
| --- | --- |
| ポートの設定 | モード（アクセス / トランク）・アクセス VLAN・許可 VLAN（`10,20` / `100-110` / `all`）・ネイティブ VLAN。VLAN ID は 1〜4094。トポロジー図の VM をクリックすると設定パネルが開く。不正な値は理由を出して反映しない。変えたポートで覚えた MAC は消す |
| 既定 | すべてアクセス VLAN 1（以前の版と同じ動き） |
| アクセスポート（受信） | タグなしを受け、アクセス VLAN のフレームとして扱う。**タグ付き（VLAN ID が 0 以外）は捨てる**（`vlan-tagged-access`）。VLAN ID 0（優先度だけのタグ）はタグなしと同じ |
| アクセスポート（送信） | タグなし |
| トランク（受信） | タグ付きはその VLAN（許可に無ければ捨てる: `vlan-not-allowed`）。タグなしはネイティブ VLAN（ネイティブが許可に無ければ捨てる）。ネイティブ VLAN のタグ付きも受ける |
| トランク（送信） | ネイティブ VLAN はタグなし、それ以外はタグを付ける。優先度（PCP）は受けたときのものを保つ（タグなしで来たら 0） |
| 転送 | 同じ VLAN に属するポートにだけ。**VLAN をまたぐ通信は、ルーターを通らない限り届かない** |
| 捨てるフレーム | タグが途中で切れている（`vlan-malformed`）、VLAN ID 4095（`vlan-invalid`）、802.1Q 以外のタグ 0x88a8・0x9100（`vlan-unsupported`）、**二重タグ**（`double-tag`）。どれも例外を投げず、理由を記録する |
| ハブのとき | VLAN を見ない（タグもそのまま全ポートへ） |
| MTU | タグ付きの最大は 1518 バイト（ゲストのドライバが、それより長いフレームを捨てる） |

**ネイティブ VLAN と二重タグ（VLAN ホッピング）**: VLAN ホッピングの「二重タグ」攻撃は、攻撃者がネイティブ VLAN と同じアクセス VLAN にいて、
外側 = ネイティブ VLAN・内側 = 攻撃先の VLAN の二重タグのフレームを送り、1台目のスイッチが外側を外してネイティブ VLAN のままトランクへ（タグなしで）流し、
2台目のスイッチが内側のタグで攻撃先の VLAN に入れてしまう、というもの。このスイッチでは:

- アクセスポートは**タグ付きのフレームをすべて捨てる**（VLAN ID 0 を除く）ので、アクセスポートからは二重タグも1重のタグも入らない
- トランクでも、**二重タグ（外側の後ろがまたタグ）は捨てる**。Q-in-Q（0x88a8）も扱わない
- ネイティブ VLAN はトランクの上でタグなしになる（本物のスイッチと同じ）。ネイティブ VLAN を、ホストの使っていない VLAN にする（設定パネルで変えられる）のが本物の対策
- 将来、攻撃の教材にするときは、`ingress()` の二重タグの判定を外せば「タグを1つ外して、残りのタグのまま転送する」動きを作れる（今はしない）

### MAC アドレステーブル（VLAN ごと）

- テーブルは **VLAN ごと**に持つ。同じ MAC が別の VLAN にあっても混ざらない（例: ルーター R の MAC は VLAN 1・10・20 にそれぞれ1件ずつ、どれもポート P8）。画面の表に VLAN 列がある
- 上限は **VLAN ごと 1024 件、全体 2048 件**。ある VLAN で MAC フラッディングが起きても、ほかの VLAN は学習を続けられる（全体の上限まで）。
  上限に達したときの振る舞い（新しい MAC は覚えない → その宛先はフラッディング）は以前と同じ

### 演習（学習: L3・VLAN）

最初に、A を LAN1（VLAN 10）、B を LAN2（VLAN 20）にし、R を起動する（足りないものは足す。3台がそろうまで、この環境で約 20 秒）。

1. **ルーターを越える ping**: A の `ip route`（`default via 10.5.1.1`）→ B へ `ping`（返事が **ttl=63**。64 からルーターで 1 減った）→
   `traceroute -n`（1ホップ目 10.5.1.1、2ホップ目 10.5.2.2）→ `ping -c 1 -t 1`（ルーターが **Time to live exceeded** を返す）→ R の `ip route`
2. **ゲートウェイ未設定の失敗**: A で `ip route del default` → ping は **`Network is unreachable`**（送ることもできないので、キャプチャにも出ない）→ `route add default gw 10.5.1.1` で戻す
3. **ip_forward OFF の失敗**: R で `echo 0 > /proc/sys/net/ipv4/ip_forward` → A の ping は **100% packet loss**（キャプチャでは A → R の request だけで、R → B が出ない）→ ON に戻す
4. **VLAN 分離**: A と B を同じ LAN1（10.5.1.0/24）にして、B のポートだけ VLAN 20 にする → ARP が届かず通らない → VLAN 10 に戻すと通る
5. **VLAN 間ルーティング**: R のケーブルを抜くと VLAN 10 → 20 は通らない。差し直すと R のトランク経由で通る（ttl=63）
6. **トランクのタグを観察**: キャプチャのフィルタを `vlan` にして ping。R のトランクから入ってきたフレームに 802.1Q のタグ（VLAN 10 / 20）。
   一覧の VLAN 列の `[20]` は「タグ付きで入ってきた」、経路の `R[10]` は「R のポートへ VLAN 10 のタグを付けて出した」という意味

## パケットキャプチャ

### 仕組み

- 仮想スイッチは、フレームを1つ処理するたびに `onFrame` で知らせる:
  `{ frame, inPort, outPorts, decision, reason, ts }`
  - `inPort` / `outPorts` はポートの番号。届けた先を配列で持つ（ハブ・フラッディングでは複数）。一覧の「経路」は `A → B, C` のように出る
  - `decision` は転送の判断（`hub` / `known` / `flood` / `broadcast` / `filtered`）
  - `vlan`（スイッチの中で扱った VLAN）・`inTag`（入ってきたときのタグ）・`outTags`（出ポートごとの、出したときのタグ）
  - 捨てたら `outPorts` は空で、`reason` に理由（`cable` ケーブルが抜けている・`loss` 損失の設定・`no-port`・`runt` 短すぎる・`filtered` 同じポート）。
    一部の届け先だけ捨てたとき（ケーブルを抜いた直後のフラッディングなど）は、転送した扱いで理由だけ残る
  - `ts` は `performance.timeOrigin + performance.now()`（UNIX 時刻のミリ秒。小数でマイクロ秒くらいまで）
- `Capture` がそれをリングバッファに記録する（フレームは複製して持つ）。ページを開いたときから記録を始め、
  「記録を止める/始める」「クリア」で操作する
- パケットモニタの集計（`TrafficStats`）も同じ `onFrame` から数える。スイッチは集計を持たないので、二重に数えない。
  モニタの数は、キャプチャの停止・クリア・上限には左右されない（モニタの「数え直す」で 0 に戻す）

### 上限

**2万件・16MB** のどちらかを超えたら、古いものから捨てる（画面に、上限と「上限を超えて消した古い記録」の件数を出す）。

- ふつうの操作（ping・HTTP・TCP のやりとり）では、数分で数百件ほど。2万件あれば、演習1回ぶんは丸ごと残る（MAC フラッディングの演習は1回で約1100件）
- フレームは最大でも約1.5KB なので、2万件でも30MB ほど。バイト数でも上限をかけて、大きなフレームが続いても
  ページのメモリが増え続けないようにした（VM 2台で、ページ全体はもともと約0.5GB 使う）
- 上限は `capture.js` の `DEFAULT_LIMITS` で変えられる

### pcap の形式

外部ライブラリは使わず、`pcap.js` で書き出す（[pcap-savefile(5)](https://www.tcpdump.org/manpages/pcap-savefile.5.html)）。

| 項目 | 値 |
| --- | --- |
| バイト順 | リトルエンディアン |
| マジックナンバー | `0xa1b2c3d4`（時刻はマイクロ秒）。`writePcap(records, { nano: true })` で `0xa1b23c4d`（ナノ秒）も書ける |
| バージョン | 2.4 |
| thiszone / sigfigs | 0 / 0（時刻は UTC） |
| snaplen | 262144 |
| リンクタイプ | 1（Ethernet） |
| 各レコード | ts_sec・ts_usec・incl_len・orig_len（各 u32）+ フレーム |
| ファイル名 | `v86-link-YYYYMMDD-HHMMSS.pcap`（ダウンロードしたときのローカル時刻） |

既定はマイクロ秒。ブラウザの時計（`performance.now()`）はマイクロ秒より細かくなく、UNIX 時刻のミリ秒を浮動小数点で持つと
0.24µs 程度で丸まるので、ナノ秒にしても意味のある桁は増えない。
既定では転送したフレームだけを書き出す。「捨てたフレームも pcap に入れる」を選ぶと、捨てたものも入る
（pcap には「捨てた」という印を付ける欄が無いので、区別は画面で見る）。

**1フレーム = 1件。** ハブやフラッディングで複数のポートへ届けても、記録は入ってきたときの1件だけ（`outPorts` が複数になる）で、
pcap にも1回だけ書く（e2e で、3台・ハブ/スイッチ/フラッディングを混ぜて「pcap の件数 = キャプチャの件数」「A↔B の ICMP の数が同じ」ことを確かめた）。

**VLAN タグは「入ってきたときの形」で書く。** 記録するフレームは、スイッチのポートに入ってきたときのバイト列そのまま。
トランク（R のポート）からタグ付きで入ってきたフレームは**タグ付きのまま** pcap に入るので、Wireshark・tcpdump -e・tshark・scapy でタグ（VLAN ID・優先度）が見える
（テストで確認: `tcpdump -e` で `vlan 20, p 5`、tshark の `vlan.id`、scapy の `Dot1Q`）。
アクセスポートから入ってトランクへタグを付けて出したフレームは、記録はタグなし（入ったときの形）で、出したときのタグは画面の経路・詳細（`outTags`）で見る。
1フレームを入りと出の2回書くと「1フレーム = 1件」が崩れるので、そうしていない。

**ポートの情報は pcap に入れない。** 従来の pcap 形式にはコメントやインターフェースの欄が無い。pcapng なら
パケットごとのコメント（`opt_comment`）やインターフェース ID で入れられるが、要件で必須ではなく、形式を変えると
今の `tcpdump -r` / dpkt での確認などがすべて変わるので、今回は従来の pcap のままにした。入ったポート・出たポートは画面の一覧と詳細で見る
（送信元 MAC からも、どの VM かは分かる: 02:00:0a:05:00:NN）。

`tcpdump -r`・`tshark -r`（Wireshark と同じ解析エンジンのコマンド版）・Python の dpkt / scapy で読めることを確かめた（下の「自動テスト」）。
Wireshark の画面（GUI）では開いていない。

### 解析できるプロトコルと限界

| 層 | 解析するもの |
| --- | --- |
| Ethernet II | 宛先・送信元 MAC（ブロードキャスト・マルチキャストの印）、タイプ |
| 802.1Q | VLAN ID・優先度（PCP）・DEI・中のタイプ。2つまで（二重タグ・0x88a8 の外側タグも表示）。3つ以上・途中で切れたものは Malformed。一覧の概要の先頭に `[VLAN 20]` |
| ARP | 操作（request / reply）、送信元・宛先の MAC と IP。概要は `Who has 10.5.0.3? Tell 10.5.0.2` / `10.5.0.3 is at …` |
| IPv4 | ヘッダ長・全長・ID・フラグ（DF/MF）・フラグメントオフセット・TTL・プロトコル・送信元・宛先。一覧に TTL 列（IPv6 はホップリミット） |
| ICMP | タイプ・コード。echo request / reply は ID とシーケンス番号。Time exceeded・Destination unreachable は内容（`Time to live exceeded in transit` など）と、元のパケット（`元: 10.5.1.2 → 10.5.2.2`、プロトコル・TTL） |
| TCP | ポート・シーケンス番号・確認応答番号・ヘッダ長・フラグ（SYN/ACK/FIN/RST/PSH/URG）・ウィンドウ・データ長 |
| UDP | ポート・長さ |
| IPv6 | 送信元・宛先・次のヘッダ・ホップリミット。ICMPv6 は種類（Neighbor solicitation など）だけ |
| それ以外 | `Unknown (ethertype=0x....)` |

- **壊れたフレーム**（短すぎる・長さの欄が嘘・ヘッダ長が不正など）は、読めたところまで出して `[Malformed: …]` を付ける。
  解析は読む前に必ず長さを確かめ、どんなバイト列でも例外を出さない（テストで、でたらめなフレーム 5000 個を与えている）
- **Wireshark との違い**: TCP の Seq/Ack は生の値（Wireshark の既定は、接続の最初からの相対値）。
  TCP のオプション・IP のオプションの中身・IPv6 の拡張ヘッダ・フラグメントの再組み立て・アプリケーション層（HTTP など）は解析しない。
  802.1Q のタグは読む（上の表）
- **フィルタ**は簡単な文字列条件（空白区切りで AND）: `tcp` `udp` `icmp` `arp` `ipv6` `malformed` `unknown`、`dropped`（捨てた）、
  `10.5.0.2` または `ip:10.5.0.2`、`8080` または `port:8080`、`syn` `fin` `rst` `psh`、
  `vm:c`（C のポートに入った・出た）/ `in:a`（A のポートから入った）/ `out:b`（B のポートへ出た。名前の代わりに `p1`〜`p8`、ルーターは `r`）、
  `vlan 10` / `vlan:10`（スイッチの中で VLAN 10 だったもの、またはタグが 10）、`vlan` / `tagged`（タグ付きのフレーム）、`ttl:63`、
  それ以外の語は概要に含まれる文字。
  詳細の「この TCP 接続だけ表示」は、2つの IP と2つのポートで絞り込む（同じ組み合わせで張り直した接続も一緒に出る）

### セキュリティ（このおもちゃを攻撃・防御の教材にするときのため）

- フレームの中身は、ゲスト VM が作る**信用できない入力**として扱う。解析結果・16進ダンプ・ASCII 表示はすべて
  `textContent` で画面に入れ、`innerHTML` は使っていない（テストで、`<img onerror>` や `<script>` を含むフレームを注入し、
  要素が作られず実行もされないことを確かめている）
- VM の名前・トポロジー図・MAC テーブルのラベルは、このページが決めたもの（A〜H・R、IP、P1〜P8、VLAN）だけを使う。ゲストのホスト名やターミナルの文字列は表示のラベルにしない。
  ターミナルの出力は xterm.js に渡すだけ、それ以外の DOM への挿入はすべて `textContent`（SVG も `createElementNS` + `textContent`）
- ルーターのパネルの `ip route` の出力（ゲストが出した文字列）も、制御文字・エスケープシーケンスを除いて `textContent` で表示する（e2e で、
  ゲストの `ip` を `<img onerror>` を出す関数に差し替えても、要素が作られず実行もされないことを確かめている）
- 解析は範囲外を読まず、例外を出さない（上記）。スイッチ・VLAN・VlanLink も、壊れたフレーム（短すぎる・Ethernet ヘッダが欠ける・タグが切れている・
  VLAN ID が範囲外・二重タグ・バイト列でない）で例外を投げない。MAC テーブルの上限は VLAN ごと + 全体
- MAC アドレステーブルには上限（1024 件）があり、MAC フラッディングでページが重くならない（上の「MAC アドレステーブルの仕様」）
- 仮想スイッチにもルーターにも外への出口（アップリンク）は無い（つないだ VmNode の間でだけフレームをやりとりする。ルーター R も、このページの中の VM の1台）。CDN や分析などの外部への通信も無い。
  e2e で「ページの外（別のホスト）への http(s) の通信が1つも無い」ことを毎回確かめている
- **CSP（`<meta http-equiv="Content-Security-Policy">`）**: 以前の版には CSP が無かった（「既存のものを維持」できるものが無かった）ので、
  同じオリジンだけを許す CSP を足した:
  `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self'; worker-src 'self' blob:; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'`
  - `'wasm-unsafe-eval'` は v86（WebAssembly と、ゲストのコードを実行時に WebAssembly にする JIT）に必要。`'unsafe-eval'`（JS の eval）は許していない
  - `style-src 'unsafe-inline'` は xterm.js と、要素の `style` 属性（仮想スクロールの位置など）に必要
  - v86 のスピーカーは `blob:` の URL から AudioWorklet を読み込むので CSP で止まる。音は使わないので `disable_speaker: true` にした
  - e2e で CSP の違反（`securitypolicyviolation`）が1つも起きないことを確かめている

### 既知の制約（キャプチャ）

- 記録は**ページの中（メモリ）だけ**。リロードすると消える。残したいときは pcap をダウンロードする
- 記録できるのは**仮想スイッチを通ったフレームだけ**。VM の中で閉じた通信（自分自身への通信など）は見えない（VM の中で `tcpdump -i lo` を使う）
- 一覧は仮想スクロールで、見えている行だけを作る。フィルタを変えたときは、残っている記録（最大2万件）をすべて見直す
- 一覧の時刻は「キャプチャの開始（またはクリア）からの秒」。pcap には UNIX 時刻（UTC）で入る

## 既知の制約

- **重い。** 全台の x86 エミュレータがページのメインスレッドで動く（上の表）。台数を増やすほど、起動中・通信中の画面が引っかかる
- **外のネットワークにはつながらない。** VM の間だけの LAN（ゲストから外へは出られないし、外からも入れない）
- **リロードすると、全台が最初の状態（A・B の2台）に戻る。** ゲストの中で作ったファイルや設定は残らない
- ゲストには `nc` と `httpd` が無いので socat で代わりにしている。MAC フラッディングの道具（macof など）も無いので、偽のフレームはページから入れる
- MAC はゲストの中で変えているので、ゲストで `ifconfig eth0 hw ether …` を打てば別の MAC にもできる（スイッチはそれを覚えるだけ）。
  変える前（起動直後〜ネットワーク設定まで）は v86 のランダムな MAC（00:22:15:…）でフレームを出すことがあり、それも一時的にテーブルに入る
- ハブ・スイッチの切り替えで MAC テーブルは空になる。直後の最初のユニキャストはフラッディングになることがある（演習2の注を参照）
- ターミナルの大きさは、起動したときとウィンドウの大きさを変えたときに `stty cols/rows` でゲストに伝える。
  その間にコマンドを実行中だと、`stty` の行がそのコマンドの入力になってしまう
- トポロジー図の光り方は 0.35 秒の表示で、1秒に何百フレームも流れると、ずっと光ったままに見える
- MAC テーブルの画面は、エントリが多いとき（MAC フラッディングの後など）、新しい 200 件だけ表示する
- **ルーターの VLAN のタグは JS（VlanLink）が付け外しする。** ゲストの Linux に 8021q が無いため（上の「ルーターの方式」）。ゲストの `tcpdump -e` には、タグを外したあとのフレームしか見えない
- VlanLink は宛先の IP のサブネットで VLAN を決めるので、ポートの設定パネルでホストを別の VLAN に移しても、ルーターはサブネットの VLAN にしか送らない
  （「サブネットごとに VLAN を分ける」を OFF/ON するか、サブネットを選び直すと、自動の割り当てに戻る）
- ルーターは1台だけ（P8）。ゲストに iptables が無いので、フィルタ（ACL）や NAT の演習はできない
- ルーターがいると、ルーターが送る IPv6 のマルチキャスト（タグなし = ネイティブ VLAN 1）は、VLAN 1 にほかのポートが無ければ「ほかにポートが無い」として捨てた記録が残る

## 別のエンジン（container2wasm など）に差し替えるときの考え方

UI と仮想スイッチは `VmNode` のインターフェースだけを使っていて、v86 のことは知らない。差し替えるときは、`VmNode` を継承したクラスを1つ作る。

| `VmNode` に必要なもの | v86 では | 別のエンジンでは（考え方） |
| --- | --- | --- |
| `start()` / `stop()` | `new V86({...})` / `destroy()` | エンジンの起動と停止。終わったら Promise を解決する |
| `writeSerial(text)` | `serial_send_bytes(0, UTF-8)` | ゲストの標準入力（コンソール）へバイト列を書く |
| `"serial"` イベント | `serial0-output-byte` をまとめて流す | ゲストの標準出力（コンソール）からのバイト列 |
| `"frame"` イベント | `net0-send`（Ethernet フレーム） | ゲストの NIC が送った Ethernet フレーム |
| `injectFrame(frame)` | `bus.send("net0-receive", frame)` | ゲストの NIC にフレームを渡す |
| `"progress"` イベント | `download-progress` / `emulator-ready` | ダウンロードと起動の進み具合 |

- **やりとりの単位を Ethernet フレームにそろえる**のがポイント。エンジンがゲストの NIC のフレームを JS に出せるなら、
  それを `"frame"` で出し、届いたフレームを NIC に渡す `injectFrame` を作れば、スイッチはそのまま使える。
  フレームではなく IP パケットや TCP の単位でしか出せないエンジンの場合は、そのノードの中で Ethernet フレームに包み直す
  （逆も同じ）必要がある。container2wasm がブラウザの中でフレームをどう受け渡せるかは、まだ確かめていない
- **エンジンを混ぜられる。** スイッチはポートごとに `VmNode` を持つだけなので、A を v86、B を container2wasm にもできる
- Web Worker と SharedArrayBuffer を使うエンジンでは、**COOP/COEP（cross-origin isolation）が要る**。
  そのときは、このリポジトリの webcontainers と同じく、Service Worker でヘッダを付ける方式（coi-serviceworker）を使う。
  v86 は要らない（確認済み）ので、今は付けていない。container2wasm で要るかどうかは、差し替えるときに確かめる
- シリアルの代わりに、エンジンによっては仮想端末（PTY）を持つものもある。`"serial"` / `writeSerial` の形にそろえれば、xterm.js 側はそのまま使える
- プロンプトの検出（`/% $/`）とネットワーク設定のコマンドは、ゲストの OS に依存する。`main.js` の先頭の設定（イメージ・コマンド・プロンプト）を差し替える
