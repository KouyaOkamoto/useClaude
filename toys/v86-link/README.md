# ブラウザ内 Linux 2台を LAN でつなぐ（v86）

同じページの中で、エミュレータ [v86](https://github.com/copy/v86) の Linux を2台起動し、仮想ネットワークでつなぐ。
左右のターミナルから、それぞれの VM を操作して、ping・HTTP・TCP で疎通を確かめられる。
**すべてブラウザの中で完結していて、サーバーも外のネットワークも使わない。**

## 構成

```
 ページ（メインスレッド）
 ┌──────────────────────────────────────────────────────────────────────────┐
 │  左のターミナル (xterm.js)                        右のターミナル (xterm.js)  │
 │      ↑↓ シリアル（ttyS0）                              ↑↓ シリアル           │
 │  ┌──────────────────────┐                     ┌──────────────────────┐   │
 │  │ VmNode「left」        │                     │ VmNode「right」       │   │
 │  │  V86Node（v86）       │                     │  V86Node（v86）       │   │
 │  │  Linux 10.5.0.2/24    │                     │  Linux 10.5.0.3/24    │   │
 │  │  NIC (ne2k)           │                     │  NIC (ne2k)           │   │
 │  └─────┬────────▲───────┘                     └─────┬────────▲───────┘   │
 │   net0-send   net0-receive                     net0-send   net0-receive  │
 │        │        │                                    │        │          │
 │  ┌─────▼────────┴────────────────────────────────────▼────────┴───────┐  │
 │  │ VirtualSwitch（MAC アドレスを覚えて転送。ケーブル・遅延・損失・集計）    │  │
 │  └────────────────────────────────────────────────────────────────────┘  │
 └──────────────────────────────────────────────────────────────────────────┘
```

| ファイル | 役割 | エンジンに依存するか |
| --- | --- | --- |

| `main.js` / `index.html` / `style.css` | 画面（ターミナル・ボタン・モニタ） | しない（`V86Node` を作るところだけ） |

## 仕組み: フレームの橋渡し

v86 公式のサンプル [`examples/two_instances.html`](https://github.com/copy/v86/blob/master/examples/two_instances.html) と同じ方式。

1. v86 の NIC（ne2k）は、ゲストがパケットを送るたびに、Ethernet フレームを `net0-send` イベント（`Uint8Array`）で外に出す。
   `net_device` に `relay_url` を指定していないので、外のネットワークにはつながらず、フレームを出すだけになる
2. `VirtualSwitch` が、送り元の MAC アドレスを覚えて、宛先のポートの VM へ渡す（分からない宛先・ブロードキャストは全ポートへ）
3. 渡された側は `emulator.bus.send("net0-receive", frame)` で、そのフレームを自分の NIC が受け取ったことにする

公式サンプルは `emulator1` の `net0-send` を `emulator2` の `net0-receive` へ直接つないでいるが、ここではその間にスイッチを入れて、
ケーブルの抜き差し・遅延・損失・集計をできるようにしている。スイッチは MAC アドレステーブルで転送するので、3台以上つないでもそのまま動く
（`sw.attach(node)` を増やすだけ。通常の JS で3ポートの転送を確かめた）。

IP は、シリアルからコマンドを送って設定する（「ネットワーク設定」ボタン）。公式サンプルの `ifconfig eth0 up arp <IP>` は
このイメージでも通るが、サブネットマスクが 255.0.0.0 になるので、マスクも指定している:

```sh
ifconfig eth0 10.5.0.2 netmask 255.255.255.0 up   # 左
ifconfig eth0 10.5.0.3 netmask 255.255.255.0 up   # 右
```

## 起動手順

```bash
# リポジトリのルートで（どの静的サーバーでもよい。COOP/COEP などの特別なヘッダは要らない）
npx http-server -p 8080
# http://localhost:8080/toys/v86-link/ を開く
```

1. 「起動」: イメージ（約10MB）を1回だけダウンロードして、2台を同時に起動する。進み具合は各ターミナルの上に出る
2. 「ネットワーク設定」: 左に 10.5.0.2、右に 10.5.0.3 を設定する（ホスト名とプロンプトも left / right にする）
3. 疎通確認のボタン（結果は各ターミナルに出る）
   - **ping 左→右 / 右→左**
   - **HTTP: 右でサーバー起動 → 左から取得**: 右で socat が 8080 番で待ち受け、接続ごとに小さなシェルスクリプトが HTML を返す。左の curl が取得する
   - **TCP: つなぐ → 文字列を送り合う → 切る**: nc の代わりに socat。右で 7000 番を待ち受け、左から接続し、打った行が相手のターミナルに出る
4. 「ケーブルを抜く」: 右の VM のケーブルを抜く（スイッチがフレームを捨てる）。ping が失敗し、戻すと通る。遅延（ms）と損失（%）も足せる

ターミナルをクリックすれば、そのまま打てる（`tcpdump -n -i eth0` でフレームを見るのも面白い）。画面の「コマンド例」に、ボタンが送るコマンドが全部ある。

### nc と httpd が無い

v86 の公式 Linux イメージ（`linux4.iso` と `buildroot-bzimage68.bin`）は、どちらも `nc` と `httpd` を持っていない（BusyBox の applet にも無い）。
`buildroot-bzimage68.bin` には socat があるので、`nc` の代わりに `socat - TCP-LISTEN:7000` / `socat - TCP:<IP>:7000`、
`httpd` の代わりに `socat TCP-LISTEN:8080,fork EXEC:<シェルスクリプト>` を使っている。詳しくは [images/README.md](images/README.md)。

## 自動テスト

```bash
node toys/v86-link/test/e2e.cjs http://localhost:8080/toys/v86-link/   # playwright が必要
```

ヘッドレス Chromium で、シリアル出力の文字列を見て確かめる: 2台がブートする / ネットワーク設定 / ターミナルへのキー入力が
それぞれの VM に届く / 日本語が化けない / 双方向 ping / HTTP 取得 / TCP の送受信 / ケーブルを抜くと ping が失敗し、差すと復旧する /
遅延 / パケットモニタ / 外への通信が無い / 再読込後の起動 / スマホ幅。あわせて、ブート時間・メモリ・ping・HTTP・入力の遅延を測る。

## 計測結果（詳しくは [docs/results.md](docs/results.md)）

この環境は CPU が遅いので、時間は 1/2〜1/3 くらいにして読むとよい。

| 項目 | 結果 |
| --- | --- |
| ダウンロードサイズ（初回） | 約12.9MB（イメージ 10.07MB は2台で共有） |
| メモリ設定 | `memory_size` 64MB × 2台 |
| ブート時間 | 初回 11.2〜11.6s、再読込後 10.9〜11.1s（2台同時。1台だけなら 5.5s） |
| ページ全体のメモリ | 約0.5GB（起動前 118MB → 2台が動いて 483MB） |
| 操作の遅延 | 1文字のエコーまで 中央値 15ms。ブート中は最大 0.2 秒ほど引っかかる |
| ping の往復 | 1.3〜9.3ms（平均 約5ms） |
| HTTP 取得 | 0.40〜0.58s |

## 既知の制約

- **重い。** 2台の x86 エミュレータがページのメインスレッドで動くので、ページ全体で約0.5GB のメモリを使い、
  ブート中は画面の操作が少し引っかかる。スマホでは厳しいかもしれない
- **外のネットワークにはつながらない。** 2台の間だけの LAN（ゲストから外へは出られないし、外からも入れない）
- **リロードすると、2台とも最初の状態に戻る。** ゲストの中で作ったファイルや設定は残らない
- ゲストには `nc` と `httpd` が無いので socat で代わりにしている。ほかのコマンドが欲しければ、イメージを作り直す必要がある
- ターミナルの大きさは、起動したときとウィンドウの大きさを変えたときに `stty cols/rows` でゲストに伝える。
  その間にコマンドを実行中だと、`stty` の行がそのコマンドの入力になってしまう

## 別のエンジン（container2wasm など）に差し替えるときの考え方

UI と仮想スイッチは `VmNode` のインターフェースだけを使っていて、v86 のことは知らない。差し替えるときは、`VmNode` を継承したクラスを1つ作る。

| `VmNode` に必要なもの | v86 では | 別のエンジンでは（考え方） |
| --- | --- | --- |
| `start()` / `stop()` | `new V86({...})` / `destroy()` | エンジンの起動と停止。終わったら Promise を解決する |
| `writeSerial(text)` | `serial_send_bytes(0, UTF-8)` | ゲストの標準入力（コンソール）へバイト列を書く |
| `"serial"` イベント | `serial0-output-byte` をまとめて流す | ゲストの標準出力（コンソール）からのバイト列 |
| `"frame"` イベント | `net0-send`（Ethernet フレーム） | ゲストの NIC が送った Ethernet フレーム |
| `injectFrame(frame)` | `bus.send("net0-receive", frame)` | ゲストの NIC にフレームを渡す |
| `"progress"` イベント | `download-progress` / `emulator-ready` | ダウンロードと起動の進み具合 |

- **やりとりの単位を Ethernet フレームにそろえる**のがポイント。エンジンがゲストの NIC のフレームを JS に出せるなら、
  それを `"frame"` で出し、届いたフレームを NIC に渡す `injectFrame` を作れば、スイッチはそのまま使える。
  フレームではなく IP パケットや TCP の単位でしか出せないエンジンの場合は、そのノードの中で Ethernet フレームに包み直す
  （逆も同じ）必要がある。container2wasm がブラウザの中でフレームをどう受け渡せるかは、まだ確かめていない
- **エンジンを混ぜられる。** スイッチはポートごとに `VmNode` を持つだけなので、左を v86、右を container2wasm にもできる
- Web Worker と SharedArrayBuffer を使うエンジンでは、**COOP/COEP（cross-origin isolation）が要る**。
  そのときは、このリポジトリの webcontainers と同じく、Service Worker でヘッダを付ける方式（coi-serviceworker）を使う。
  v86 は要らない（確認済み）ので、今は付けていない。container2wasm で要るかどうかは、差し替えるときに確かめる
- シリアルの代わりに、エンジンによっては仮想端末（PTY）を持つものもある。`"serial"` / `writeSerial` の形にそろえれば、xterm.js 側はそのまま使える
- プロンプトの検出（`/% $/`）とネットワーク設定のコマンドは、ゲストの OS に依存する。`main.js` の先頭の設定（イメージ・コマンド・プロンプト）を差し替える
